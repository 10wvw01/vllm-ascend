# 02｜一次请求端到端怎么跑：从调度器一直走到 310P

这一章先不钻任何一个 kernel。目标只有一个：脑子里建立“一次请求到底怎么跑”的完整电影。

## 1. 先把 Prefill 和 Decode 分开

用户发来一句话，模型不会一次把 2000 个输出 token 全算出来。

通常分成两个阶段。

### Prefill：先把输入吃进去

假设输入 4096 token：

```text
prompt 4096 token
   |
   v
一次或分块处理较多 token
   |
   v
建立这些 token 对应的 KV Cache
   |
   v
得到“下一个 token”的分布
```

Prefill 的典型特点：

- 一次处理的 token 数比较多；
- 大矩阵计算占比高；
- 更容易把 AI Core 喂饱；
- Attention 需要处理较长上下文。

### Decode：一个一个往后生成

得到第一个输出以后：

```text
历史 KV Cache + 新 token
        |
        v
跑一轮模型
        |
        v
产生下一个 token
        |
        v
更新 KV Cache
```

然后重复。

Decode 的典型特点：

- 单个请求每轮新增 token 很少；
- 因此单请求矩阵的 M 往往很小；
- 并发 batch 对设备利用率非常重要；
- 固定开销、通信延迟、小 shape 效率会变得特别显眼。

后面你会看到 MM+AR 专门做 small-M 路径，本质上就是在对抗 Decode 时代“小活太多、固定开销太贵”的问题。

---

## 2. “batch=10”在人话里是什么意思

在服务语境下，大家常说 batch=10，但它可能指两件不同的东西：

1. 有 10 个活跃请求；
2. 某一轮真正送进模型的 token/sequence 数组成了一个批。

vLLM 是 continuous batching，所以它不像传统离线训练：

```text
固定 10 条样本 -> 整批从头跑到尾
```

而更像：

```text
这一轮：请求 A/B/C/D... 一起推进
下一轮：A 完了，E 加入，B/C/D/E... 一起推进
```

因此以后看到 kernel 的 `M`，不要机械地等同于“用户并发数”。

`M` 更准确地表示**这次 Linear 实际一起处理了多少行 token hidden state**。

例如 speculative verify、chunked prefill、普通 decode，M 的来源都可能不同。

## 3. 一轮执行的大体链路

把很多细节先压缩成下面这张图：

```text
Engine / Scheduler
   |
   | 决定本轮 scheduled tokens / requests
   v
Worker
   |
   v
Model Runner
   |
   | 构造 input_ids / positions / slot mapping / attention metadata ...
   v
Model.forward
   |
   +--> Attention / GDN
   |
   +--> o_proj / out_proj
   |
   +--> residual / norm
   |
   +--> MoE / MLP
   |
   v
logits
   |
   +--> 普通 sampling
   |        或
   +--> speculative verify / rejection sampling
   |
   v
Scheduler 更新请求状态
```

在 310P 分支里，`vllm_ascend/_310p/model_runner_310p.py` 是非常重要的中间站。

它不是模型本身，而是负责把 vLLM 上层的“本轮计划”翻译成 310P 可以执行的输入与调用。

---

## 4. Worker、Model Runner、Model 三者不要混

### Worker

更像一个设备进程的总管：

- 当前 rank 是谁；
- NPU 环境怎么初始化；
- 分布式组怎么建立；
- 模型生命周期；
- cache 生命周期；
- shutdown 时怎么收尾。

本项目可重点看：

```text
vllm_ascend/_310p/worker_310p.py
```

### Model Runner

更像每一轮 forward 的执行导演：

- 把 scheduled request 变成 tensor；
- 建 attention metadata；
- 准备 KV block table；
- 选择 eager / graph；
- 调模型 forward；
- 处理投机推理的额外输入输出。

重点：

```text
vllm_ascend/_310p/model_runner_310p.py
```

### Model

才是 Transformer/Qwen 数学网络。

很多 Qwen 模型定义来自 vLLM 本身，本仓库通过 patch、算子替换和 quant method 等方式改变它在 Ascend/310P 上的执行方式。

这也是为什么你有时找不到一份“完整复制的 Qwen3.6 模型文件”：适配层没有必要把上游模型全部重写。

## 5. 一层 Qwen 在设备上怎么经过

先抽象成：

```text
hidden_states [M, hidden]
    |
    +---- Attention / Linear Attention ----+
    |                                     |
    |                         context/output features
    |                                     |
    +----------------> output projection -+
                          o_proj
                            |
                            v
                     TP partial output
                            |
                         AllReduce
                            |
                            v
                    residual / next block
```

本次融合就是盯住中间这个非常具体的位置：

```text
output projection MM
        +
紧跟它后面的 TP reduction
```

普通执行可能是两个不同框架组件分别负责：

```text
Linear Method:     做 MM
RowParallelLinear: 做 TP all-reduce
```

而定制以后：

```text
MemFabricMmArLinearMethod310:
    自己把 MM + TP reduction 都做完
```

所以必须把外层的 `reduce_results` 关掉，否则会发生：

```text
已经 reduce 一次
    +
框架又 HCCL reduce 一次
```

结果不仅慢，而且数值直接错成重复相加。

这就是 `configure_memfabric_mm_ar()` 设置 `layer.reduce_results = False` 的原因。

## 6. TP=2 时一层 Linear 的真实数据形状

目标融合合同固定：

```text
global K = 4096
TP = 2
local K = 2048
N = 2048
```

可以想象原始矩阵是：

```text
X: [M, 4096]
W: [4096, 2048]
```

Row Parallel 把 K 方向拆开：

```text
rank0:
X0 [M,2048] @ W0 [2048,2048] -> Y0 [M,2048]

rank1:
X1 [M,2048] @ W1 [2048,2048] -> Y1 [M,2048]
```

原始完整计算：

```text
[X0 X1] @ [W0]
           [W1]
= X0@W0 + X1@W1
= Y0 + Y1
```

所以 TP=2 的 reduction 不是额外“为了分布式而随便加的工作”，它就是把被拆开的矩阵乘法重新拼成数学上完整结果所必须的一步。

理解这个等式，后面的 MM+AR 合法性就完全清楚了。

## 7. 普通路径在时间线上是什么样

先极度简化：

```text
rank0: [ MM0 ] [ HCCL AllReduce ] [ next op ]
rank1: [ MM1 ] [ HCCL AllReduce ] [ next op ]
```

MM 先完整结束，随后进入一个通用 collective。

通用 collective 的优点是：

- 语义通用；
- 支持多 rank；
- 框架成熟；
- 不需要模型层知道网络细节。

缺点是对这个特定 TP=2、固定 shape 场景，它可能承担比实际需求更多的框架边界和同步成本，而且 MM 与通信很难按我们想要的粒度直接流水。

这给了定制优化空间。

## 8. 当前融合路径在时间线上是什么样

大 M 时，Runtime 会把 M 按 `batch_m=256*q` 切 batch。

以 3 个 batch 为例：

```text
P0 = producer batch0: MM -> signal
P1 = producer batch1: MM -> signal
W0 = wait peer batch0
A0 = add local+peer batch0
P2 = producer batch2
W1/A1 ...
```

实际 enqueue 顺序是：

```text
P0
P1
W0 A0
P2
W1 A1
W2 A2
quiet
ack
```

它想创造的硬件重叠是：

```text
SDMA(0)  || MM(1)
SDMA(1)  || wait/add(0)
SDMA(2)  || wait/add(1)
```

注意：host enqueue 顺序看上去仍然是一条流，但 AI Core 计算与 SDMA 数据搬运属于不同执行资源，因此存在并行机会。

是否真的重叠、重叠多少，必须看目标机 profiler，不能只凭代码结构断言。

## 9. Decode 为什么特别考验这个融合

普通 Decode 如果一次只有少量 token：

```text
M = 1, 8, 16, 32 ...
```

而 cooperative batch MM 的原生 batch 最小以 256 行为中心设计。

如果为了 8 行有效数据，硬算完整 256 行：

```text
有效计算：8 行
补齐计算：248 行
```

算法是对的，但效率可能很差。

所以当前实现又有 small-M exact path：

```text
M < min(batch_m,256)
        |
        v
不再按 M 切 8 核
        |
        v
按 N=2048 切成 8 个 256 列
        |
每个 core 都处理完整 M/T 行，但只算 1/8 输出列
```

也就是：

```text
M-split  ->  N-split
```

这体现一个重要性能规律：

> 同一个数学算子，Prefill/大 M 和 Decode/小 M 的最佳并行切分方式可能完全不同。

不要迷信“一套 tiling 吃遍所有 shape”。

## 10. Graph 在端到端里扮演什么角色

Eager 模式下，每轮需要 host 不断发起 kernel。

Graph 的思想可以简化成：

```text
把一组稳定的设备操作提前录下来
        ↓
之后直接 replay
```

好处主要是减少 host 侧 dispatch/launch 开销。

但 Graph 对本次融合提出很强的生命周期约束：

```text
capture 前必须准备好 context
capture 前必须 malloc scratch
capture 前必须建 weight slices
capture 前必须 warmup kernel symbols
capture 内不能做 host barrier / 动态初始化
```

因此你会在 runtime 里看到很多：

```text
if (capturing) require_ready...
else warmup/init...
```

这些代码不是“啰嗦”，而是在保证捕获出来的图是可重复执行的静态设备动作。

## 11. 投机推理会怎样改变一次 Decode

普通 decode：

```text
target model -> 1 个新 token
```

投机推理则类似：

```text
小/便宜 draft 模型：先猜 K 个 token
            |
            v
大 target 模型：一次验证这 K 个猜测
            |
            v
尽量一次接受多个 token
```

因此一次 target forward 的有效 M、position、KV slot、attention metadata 都会变复杂。

这也是为什么 `_310p/spec_decode` 不只是“多跑一个模型”，还包含大量：

- 输入展开；
- KV block/slot 映射；
- mRoPE position；
- Graph shape；
- rejection/acceptance 配套逻辑。

后面第 05 章会单独拆开。

## 12. 端到端排障时应该从哪一层看

以后遇到“输出错了”或“性能很慢”，不要一上来就进 kernel。

建议从上到下：

```text
1. Scheduler：这一轮 M / 请求状态对不对？
2. Runner：输入 shape / position / KV slot 对不对？
3. Model/route：是不是命中了想要的 310P 路径？
4. Python op：dtype / TP / prefix / quant route 对不对？
5. C++ runtime：batch/wave/arena/lifecycle 对不对？
6. Device kernel：MM / signal / wait / add 对不对？
7. Profiler：真正慢的到底是哪一段？
```

这种层次化排障能力，比记住任何一个函数名更重要。
