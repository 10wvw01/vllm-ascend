# 04｜310P 定制能力是怎么接进去的：不要把它理解成一堆特殊 if

## 1. 先看一个现象

这个分支里的 310P 代码分布在很多地方：

```text
vllm_ascend/_310p/
vllm_ascend/patch/worker/patch_idex_310.py
vllm_ascend/patch/worker/patch_qwen3_5.py
vllm_ascend/patch/worker/patch_qwen3_dflash.py
vllm_ascend/_310p/quantization/
vllm_ascend/_310p/spec_decode/
csrc/_310P/
cmake/memfabric_310p.cmake
...
```

如果只把它理解成“兼容老卡的特殊代码”，会漏掉核心设计：

> 310P 定制是在尽量保留 vLLM 上层协议的前提下，替换一条完整的硬件执行纵向链路。

---

## 2. 为什么不直接 fork 一份完整 vLLM

最粗暴的方案当然可以：

```text
复制整个 vLLM
所有 310P 问题直接在副本里改
```

短期快，长期会非常难维护：

- 上游 scheduler 改了，要人工同步；
- 模型实现改了，要人工同步；
- spec decode 协议改了，要人工同步；
- 通用 Ascend 优化也吃不到；
- 很难区分哪些是通用能力、哪些是 310P 特化。

因此更合理的做法是：

```text
能复用上游语义的地方复用
必须针对 310P 改的地方局部替换
```

这就是你在项目里看到 patch、subclass、custom op、platform-specific runner 的原因。

---

## 3. 310P 定制可以分成五层

### 第一层：平台入口和 Worker

负责：

- 选择 310P 对应 worker/runner；
- 初始化设备和分布式环境；
- 管理进程生命周期。

重点看：

```text
vllm_ascend/_310p/worker_310p.py
vllm_ascend/_310p/model_runner_310p.py
```

### 第二层：patch 层

有些上游类不适合整体复制，就在启动阶段替换特定函数/类行为。

重点：

```text
vllm_ascend/patch/worker/patch_idex_310.py
vllm_ascend/patch/worker/patch_qwen3_5.py
vllm_ascend/patch/worker/patch_qwen3_dflash.py
vllm_ascend/patch/worker/patch_qwen3_dspark.py
```

这里的思想类似：

```text
通用 proposer / model 继续使用
        |
启动时把少数不适合 310P 的函数换成 310P 版本
```

这样能把 310P 差异压缩在较小范围。

### 第三层：算子/量化方法选择

模型代码调用的是抽象 Linear、Attention、MoE，但真正执行哪个实现，可以由 method/backend 决定。

例如：

```text
vllm_ascend/_310p/quantization/modelslim_config.py
```

它会根据 layer 是否量化、prefix、模型配置等选择：

```text
AscendLinearMethod
AscendUnquantizedLinearMethod
MemFabricMmArLinearMethod310
...
```

这就是本次融合进入模型的关键入口。

### 第四层：运行时封装

Python 最终调用 PyTorch custom op：

```text
torch.ops._C_ascend.memfabric_mm_ar_allreduce(...)
```

C++ runtime 再做：

```text
资源初始化
shape 检查
Graph 状态
arena/wave/batch 切分
kernel enqueue
错误处理
```

### 第五层：设备 kernel

AscendC 才是最底层的：

```text
MM
cache clean
ready rendezvous
SDMA signal/wait
vector add
```

五层合在一起才叫一个可服务化的 310P 定制能力。

## 4. Patch 到底是什么

“小白最容易害怕 monkey patch”，因为它看起来像运行时偷偷改函数。

你可以先把它理解成：

```text
原类 A.method
      |
初始化时
      v
替换成 310P_method
```

为什么不直接改上游原类？

因为这个差异可能只在 310P 成立。

比如 `_310p/spec_decode/dflash_proposer_310.py` 的模块注释已经说得很明确：

```text
其它平台 DFlash 输入构造使用 Triton kernel
310P 没有这条 Triton 路径
所以用 AscendC custom op 替换输入构造
```

如果直接把通用 proposer 改成 AscendC，就会污染其它平台。

因此 patch 的正确使用场景是：

> 上层协议相同，但某一小段底层实现必须按平台替换。

---

## 5. 为什么 Model Runner 也要 310P 专版

Model Runner 处在一个非常尴尬但关键的位置：它既懂 vLLM 调度数据，又懂设备执行细节。

310P 下可能要处理：

- 特定 attention metadata；
- 不同 block table 布局；
- Graph 输入稳定性；
- DFlash draft/verify 的 shape；
- 某些 int64 地址计算问题；
- 设备不支持的通用 kernel 替代。

这些都不是一个单独 Linear kernel 能解决的。

所以当你以后问“为什么这个项目改这么多文件”，答案是：

> 因为“让一个模型真正高效服务”是运行时问题，不只是算子问题。

---

## 6. 量化路由为什么是 MM+AR 的最佳接入层之一

当前融合只应该接管目标 `RowParallelLinear` 的实际计算，而不想重写 Qwen 模型结构。

ModelSlim 的 `get_quant_method()` 本来就在做：

```text
这个 Linear 到底应该用哪种方法执行？
```

因此这里天然适合加入：

```text
if 是未量化目标层 && 满足融合合同:
    return MemFabricMmArLinearMethod310()
```

好处：

- 模型类无需知道 MemFabric；
- 普通层完全不受影响；
- feature off 可自然回到 stock method；
- 权重加载/NZ 转换继续复用原未量化 method；
- 融合资格检查集中在一个地方。

这比在模型 forward 里写：

```python
if ascend_310p and layer_name == ...:
```

更干净，也更容易扩展和测试。

## 7. 为什么 custom op 是第二个关键边界

Python 如果分别调用：

```text
custom_mm()
custom_signal()
custom_wait()
custom_add()
```

框架仍然能看到很多独立边界，runtime 也难完整拥有这段流程。

当前设计对 Python 只暴露：

```text
memfabric_mm_ar_allreduce(x, weight, rank, q)
```

这相当于告诉上层：

> 你只需要给我输入和权重；从 partial MM 到最终 TP-reduced output 的生命周期由我负责。

这样 C++ Runtime 才有机会：

- 决定 batch 切法；
- 提前 enqueue 下一批 producer；
- 管理 credit；
- 一波只 quiet 一次；
- small-M 切换 N-split；
- 保证 Graph 生命周期。

所以 custom op 的价值不只是“Python 调 C++”，而是**建立优化所有权边界**。

---

## 8. 为什么 C++ Runtime 和 AscendC kernel 不能全塞一起

AscendC kernel 最适合做设备上的确定性计算和设备侧协议操作。

但以下事情更适合 host runtime：

```text
aclrtMalloc
根据环境变量配置 arena
按 M 决定 small path / batch path
管理 weight slice cache
检查 graph capture
context create/destroy
异常后标记 poisoned
```

因此合理拆分是：

```text
Python：路由与框架语义
C++：资源、生命周期、任务编排
AscendC：设备执行
```

不是语言越底层越好。放在最合适的层才是好设计。

## 9. MemFabric Adapter 为什么还要单独一层

目录里有：

```text
memfabric310p_adapter_api.h
memfabric310p_adapter.cpp
```

它位于 vLLM Runtime 和外部 MemFabric 库之间。

如果 Runtime 直接到处调用 MemFabric 各种接口，会产生强耦合：

- 外部 ABI 一变，runtime 很多地方都改；
- 容易不小心依赖 private ring/mailbox 等内部布局；
- 单测/静态审查边界模糊；
- vLLM-owned 内存和 MemFabric-owned 内存责任不清。

所以 adapter 的核心意义是：

```text
vLLM 内部只认识稳定的 mf310p_* ABI
          |
          v
adapter 把它翻译成 MemFabric public API
```

这也是为什么 header 明确写 ABI v7。

所谓 ABI，你可以先理解成：

> 两个独立模块之间约定好的二进制接口合同：函数叫什么、参数长什么样、结构体怎么布局、版本是多少。

## 10. 为什么 feature-off 也注册 custom op

`memfabric_mm_ar_binding.cpp` 会始终注册 op schema。

如果构建时没启用 MemFabric，调用时由 feature-off 实现给出明确错误。

这么做比“feature-off 时整个 op 消失”更容易排障：

```text
错误 A：Python attribute 不存在
```

很难分辨是：没编译、没注册、import 错、版本错。

而当前会明确说：

```text
当前 vllm_ascend_C 没有构建 310P MemFabric mm_ar runtime
```

这是一种工程可诊断性设计。

---

## 11. 310P 特化最重要的设计边界

以后继续加优化时，建议保持三条原则：

### 平台隔离

310P 特殊实现尽量留在：

```text
vllm_ascend/_310p
csrc/_310P
```

### 语义复用

能用通用 vLLM/vLLM-Ascend 的 scheduler、模型、接口协议，就不要复制。

### 窄接口

自定义子系统对外暴露尽量少的稳定接口，内部才自由优化。

本次 MM+AR 就是一个很好例子：模型层只知道一个 Linear Method，Python 只知道一个 custom op，runtime 只依赖 adapter ABI，device 只依赖 public signal/wait/quiet。

---

## 12. 什么时候应该新建 310P 专用实现，什么时候不该

可以用这个判断：

```text
差异只是一两个参数？
  -> 优先参数化通用实现

差异是一个小函数、上层协议完全相同？
  -> patch/subclass

差异涉及 runner 输入、graph、KV 等完整执行链？
  -> _310p 专用模块

差异是高性能设备计算？
  -> csrc/_310P AscendC/custom op
```

不要为了“代码看起来统一”把大量 310P 特殊判断塞进通用路径；也不要为了“隔离”复制整个框架。
