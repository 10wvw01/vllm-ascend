# 01｜先看懂全局地图：vLLM、vLLM-Ascend、310P 和模型是什么关系

## 1. 先不要看代码，先分清四个角色

第一次打开这个仓库，最容易产生的错觉是：“这些 Python、C++、AscendC 文件是不是都在实现模型？”

不是。可以把整个系统想成一家餐厅：

```text
Qwen3.6 模型      = 菜谱：规定要做哪些计算
vLLM             = 店长：决定哪些订单一起做、什么时候做
vLLM-Ascend      = 昇腾厨房适配层：把通用做法换成 NPU 能高效执行的做法
310P             = 真正的厨房硬件：有自己的计算核心、内存、通信和限制
```

模型告诉我们“数学上应该算什么”；推理框架决定“如何批量、缓存、调度”；硬件适配决定“在这块芯片上具体调用什么算子、怎样排布数据”；硬件最后真正执行。

这四层混在一起看，会觉得工程巨大而混乱。分开以后，事情会简单很多。

---

## 2. vLLM 到底解决什么问题

如果只想让大模型“算对”，最简单的方法是：来一个请求就把模型从头到尾跑一遍。

线上服务不能这么干，因为：

- 不同用户会同时发请求；
- 每个请求输入长度、输出长度都不同；
- Decode 每次通常只新产生少量 token；
- Attention 需要反复使用历史 K/V；
- GPU/NPU 最怕大量零碎、小算子和低利用率执行。

所以 vLLM 的主要价值不是发明 Transformer，而是把“服务请求”整理成硬件更喜欢的执行形态。

你现在先记四个关键词：

### Scheduler

决定这一轮让哪些请求进入模型、每个请求推进多少 token。

### Continuous batching

不是等 10 个请求全结束再换下一批，而是请求可以动态加入、退出。这样设备尽量一直有活干。

### KV Cache

历史 token 的 Key/Value 不重复计算，而是存起来，Decode 时直接继续用。

### Model Runner

把调度器给出的“本轮任务”整理成设备输入，然后真正调用模型 forward。

所以一条非常粗略的链是：

```text
请求
 -> Scheduler 选本轮工作
 -> Model Runner 准备 tensor / metadata / KV 地址
 -> Model forward
 -> logits / sampling
 -> 更新请求状态
 -> 下一轮
```

这就是以后读 `model_runner_310p.py` 时的背景。

## 3. vLLM-Ascend 为什么存在

上游 vLLM 最初大量能力围绕 CUDA/GPU 构建。昇腾 NPU 的运行时、算子库、Graph、通信库、内存格式和编程模型都不完全相同。

因此 vLLM-Ascend 的作用可以概括成一句话：

> 尽量保持 vLLM 上层的调度和模型语义不变，把真正依赖硬件的部分换成昇腾实现。

典型内容包括：

```text
PyTorch CUDA/NCCL 语义
        ↓
torch_npu / CANN / HCCL / AscendC
```

但“适配”不是简单搜索替换。不同硬件的最佳执行方式往往不同，因此 vLLM-Ascend 里还会有：

- 自定义 attention backend；
- 自定义量化算子；
- MoE 专用实现；
- NPU Graph 适配；
- 分布式通信适配；
- 某些型号芯片的专门 workaround 和优化。

本项目的 310P 能力就属于最后一种，而且规模已经不只是一个 workaround，而是一套平台化定制。

## 4. 为什么又单独有 `_310p`

看这个目录：

```text
vllm_ascend/_310p/
```

里面不是只有一个算子，而是能看到：

```text
attention/
model_runner_310p.py
worker_310p.py
block_table.py
quantization/
spec_decode/
ops/
fused_moe/
dflash_*.py
graph_input_contract.py
...
```

这说明一件很重要的事：

> 310P 定制不是“给某个算子加 if”，而是从 Worker、Runner、Graph、Attention、KV、量化、投机推理一直延伸到 Kernel 的纵向适配。

为什么需要这样？因为较老或定位不同的芯片，在以下能力上可能和当前主流训练/推理卡存在差异：

- 某些算子支持情况；
- 数据类型与数据格式；
- Graph 捕获行为；
- Triton 是否可用；
- Kernel 首启行为；
- 通信能力；
- 小 shape 性能；
- 内存容量与带宽。

一个合理工程做法就是把这些差异尽量隔离到 `_310p`，避免把大量型号判断散落到全仓库。

## 5. Qwen3.6 在这里处于哪一层

Qwen3.6 决定每一层模型该做什么数学计算，例如：

```text
hidden states
  -> attention / linear attention
  -> output projection
  -> residual
  -> MoE / MLP
  -> ...
```

而这个仓库重点做的是：

```text
同样的 Qwen3.6 数学
如何在 310P 上正确并且尽可能快地执行
```

需要注意：当前代码识别文本模型时使用的 HF `model_type` 名字是：

```text
qwen3_5_moe_text
```

但相关注释和目标 checkpoint 覆盖 Qwen3.5/3.6 这一模型族。不要因为变量名里写着 `35` 就误以为这条代码和 Qwen3.6 无关。框架内部的 `model_type` 是配置协议名，不一定随着营销/发布名称同步改名。

## 6. Python、C++、AscendC 分别干什么

本项目尤其需要建立这个层次感。

### Python：决定“走哪条路”

例如本次 MM+AR：

```text
vllm_ascend/_310p/quantization/modelslim_config.py
vllm_ascend/_310p/ops/memfabric_mm_ar.py
```

主要负责：

- 判断模型/层/shape/TP/dtype 是否满足融合条件；
- 把普通 Linear Method 换成定制 Method；
- 调用注册好的 custom op；
- 处理框架生命周期和 fallback。

### C++ Runtime：决定“设备任务怎样排队”

```text
csrc/_310P/memfabric_mm_ar/memfabric_mm_ar_runtime.cpp
```

它关心：

- 分配 arena / scratch；
- 初始化 MemFabric context；
- wave/batch 怎么切；
- kernel 什么时候 enqueue；
- Graph capture 能不能做 malloc；
- 失败后 context 能不能继续用；
- MM、wait、add 怎样形成流水。

### AscendC：决定“AI Core 真正怎么算”

```text
csrc/_310P/memfabric_mm_ar/memfabric310p_device.asc
```

它关心：

- 8 核怎样分 M 或 N；
- Matmul tiling；
- cache clean；
- ready cell；
- signal/wait/quiet；
- 本地 FP16 Add。

以后读代码如果不知道自己在哪一层，就先问：

```text
现在这段代码是在做“策略选择”、
“运行时编排”，
还是“核心计算”？
```

## 7. 通信又是什么角色

TP=2 意味着同一层模型被两张卡共同完成。

本次融合关注的是 Row Parallel Linear。数学形式先简化成：

```text
rank0: Y0 = X0 @ W0
rank1: Y1 = X1 @ W1
最终:  Y = Y0 + Y1
```

所以每张卡完成自己的 MM 以后，并不能直接把 `Y0` 或 `Y1` 当最终结果。两边还必须合起来。

普通实现通常是：

```text
MM
 -> 通用 HCCL AllReduce
 -> final Y
```

当前定制路径变成：

```text
MM 到本地 send arena
 -> MemFabric 把 partial output 送到 peer recv arena
 -> 每张卡本地做 send + recv
 -> final Y
```

因为 TP 固定为 2，所以“两边互换一次 partial + 本地加法”就足以完成 AllReduce 的语义。

这就是 MM+AR 项目最核心的数学基础。后面所有复杂的 ready、credit、pipeline 都是在保证这件简单的数学**更快而且不会读错数据**。

## 8. 推理性能为什么是系统问题

假设某个 MM 本身只需要 100 μs，但周围还有：

```text
kernel launch        20 us
同步                  30 us
通信                 100 us
格式转换              40 us
memset                200 us
```

那你把 MM 优化到 80 μs，端到端只省 20 μs。

反过来，如果通过系统重排做到：

```text
MM(n+1) 与 SDMA(n) 重叠
```

即使 MM kernel 一条指令都没变，总时间也可能下降很多。

因此这个项目后半程重点不是“会写 AscendC”就结束了，而是要学会：

> 从端到端时间线上判断真正的关键路径，再决定要改 kernel、内存、通信、调度还是 Graph。

这也是为什么后续专门安排性能方法论一章。
