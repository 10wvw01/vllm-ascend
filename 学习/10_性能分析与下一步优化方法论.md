# 10｜性能分析与下一步优化方法论：不要问“还能怎么快”，先问“时间花在哪”

## 1. 性能优化最重要的第一步：不要猜

看到代码以后很容易产生一串想法：

```text
q 改成 4 会不会快？
lookahead 改成 2 会不会快？
把 add 也塞进 MM kernel 会不会快？
ready 能不能去掉？
```

这些都可以成为假设，但不能直接成为结论。

正确顺序应该是：

```text
真实 workload
  -> 建 baseline
  -> profiler 定位关键路径
  -> 提出一个可证伪假设
  -> 做最小改动
  -> correctness
  -> micro benchmark
  -> end-to-end
  -> 决定保留/回退
```

---

## 2. 先区分三类性能指标

### 吞吐 Throughput

例如：

```text
tokens/s
requests/s
```

适合看高并发总能力。

### TTFT

Time To First Token。

主要受：

- Prefill；
- 排队；
- 首次编译/warmup 是否进入正式流；
- prompt 长度。

### ITL / TPOT

输出 token 之间的间隔。

Decode 优化尤其关注。

一个优化可能：

```text
吞吐变好
但单请求 ITL 变差
```

所以先明确产品目标，不能只盯一个 kernel μs。

---

## 3. 为 MM+AR 建一个最简单性能模型

Stock：

```text
T_stock(M)
= T_mm(M)
+ T_hccl_ar(M)
+ T_framework_boundary(M)
```

Fused：

```text
T_fused(M,q)
= T_prepare/gate
+ T_pipeline(M,q)
+ T_quiet/ack
+ T_tail/small_extra
```

其中 pipeline 继续拆：

```text
producer MM
cache clean + ready
SDMA
wait
local add
launch/dispatch
```

这张拆分表的意义不是算出完美公式，而是确保每个优化建议都能回答：

> 我具体打算减少哪一项？

---

## 4. 先看 shape 分布，再谈 kernel

真实 serving 中应该统计：

```text
M histogram
```

例如可能得到：

```text
M <= 16       35%
17..64        25%
65..255       15%
256..511      10%
512+          15%
```

如果 75% 都是 M<256，那么大 M pipeline 再优化 20% 也未必比 small path 快 10% 更有价值。

DFlash 开启后 histogram 还可能变化，所以要分别测：

```text
normal decode
DFlash decode
prefill
mixed serving
```

优化优先级必须跟真实 shape 权重绑定。

---

## 5. 当前代码已经告诉我们的几个历史瓶颈

源码注释记录过一些实机观察：

### ready clear 固定成本

因此 eager 使用 monotonic generation，避免每 wave 清控制区。

### tail 大 memset

因此 scratch 只 zero once，后续尾批只覆盖有效前缀。

### small-M M-split 权重流地板

因此改为 N-split，每核只读 1/8 权重。

### 通用 add 首次动态 shape 编译

因此自定义 shape-agnostic Add kernel。

这些案例共同说明：

> 小 M / Decode 优化经常不是 FLOPs 不够快，而是固定成本占比太高。

但代码里的历史微秒数字只能用来理解决策背景，不能代替当前环境重新测量。

---

## 6. 怎样判断 q=1/2/4

不要只跑单个 M。

至少做矩阵：

```text
M = 1, 8, 16, 32, 64, 128, 255,
    256, 257, 512, 1024, 2048, 4096, 8192

q = 1, 2, 4
```

注意边界：

```text
M=255/256/257
```

特别重要，因为它正好跨 small path / normal path 或 batch 边界。

对每个点记录：

```text
总 latency
producer MM duration
SDMA duration
add duration
padding ratio
batch count
实际 overlap
```

最后再按真实 M histogram 加权。

一个 q 在单点最快，不代表线上最好。

---

## 7. q 的理论权衡怎么想

### q 大

```text
+ 单 batch MM 更饱满
+ signal/wait 次数少
+ launch 固定成本少
- 首个 communication 更晚
- pipeline 更粗
- tail padding 更可能大
- 同样 arena 能放的 batch 少
```

### q 小

```text
+ 更早启动 SDMA
+ pipeline 更细
+ tail 平均浪费小
- batch 数更多
- protocol/kernel launch 次数更多
- 小 per-core M 可能降低 MM 效率
```

所以最佳 q 取决于：

```text
T_mm(batch_m)
T_sdma(payload)
固定 launch/protocol 开销
M 分布
```

这就是为什么未来一个自然方向是 q autotune，但在实现前要考虑 Graph/arena/context 当前都假设 q 在 worker 生命周期固定。

## 8. 怎样判断 lookahead=1 是否够

先看 profiler。

如果时间线是：

```text
MM1 与 SDMA0 已经高度重叠
W/A0 很短
SDMA engine 基本没有气泡
```

加 lookahead 未必有价值。

如果看到：

```text
AI Core 因 wait 停顿
SDMA 经常空闲
```

则可能尝试更深 in-flight。

但 lookahead 加深会引入：

- 更多 arena slot 同时活跃；
- mail 次序更复杂；
- 更难证明 credit 安全；
- Graph command 数更多。

因此先用 timeline 找到“气泡”，再决定是否增加深度。

---

## 9. 怎样判断 small-M N-split 还能不能优化

当前模板：

```text
T = 16/32/64/128/256
每 core N=256
8 个 weight slices
```

可以研究的轴：

### T bucket

例如是否需要：

```text
8,16,32,64,128,256
```

更细 bucket 能少 padding，但增加 symbol/warmup/graph 复杂度。

### N split 数

当前正好 8 core × 256。

可以测试其它 core 数，但要考虑权重流和 parallel overhead。

### baseN/baseK

代码已经记录某些替代 tiling 历史上更差，但软件版本变化后仍可以有计划地复验，而不是盲试。

### weight slice cache

每个 weight 约额外 8 MiB。

要统计：

```text
实际融合层数 × 8 MiB
```

如果模型层数多，这个内存换时间的代价必须纳入总容量评估。

---

## 10. “把 add 融进 MM”真的一定更快吗

直觉会说：

```text
少一个 add kernel = 更快
```

但问题是 peer partial 在 MM 结束时未必已经到达。

如果强行让 MM kernel 等 peer 数据：

```text
AI Core 可能空转等待通信
```

反而破坏：

```text
MM(n+1) || SDMA(n)
```

所以真正应该问：

```text
融合 add 后能省多少 launch/GM traffic？
会不会把通信依赖拉回 AI Core 关键路径？
```

可能更有价值的方向是：

```text
add 与“下一个本来就要读 final Y 的算子”融合
```

但这需要重新检查数学和数据依赖。

---

## 11. 是否可以边搬运边规约

这是很自然的下一步思路。

现在逻辑是：

```text
一个 batch SDMA 完成
 -> wait mail
 -> add 整个 valid batch
```

更细粒度方案可能想：

```text
搬到一部分 tile
 -> 立刻 add tile
同时后面的 tile 继续搬
```

理论上可以进一步重叠 SDMA 与 vector add。

但落地前必须确认 MemFabric public API 是否能表达：

- 子 batch / tile 完成事件；
- 对应 dst/len/mail 语义；
- 多个 in-flight tile 的有序性；
- credit 如何保护更细 slot。

如果 public API 只在整次 signal 完成后提供 mail，那么 vLLM 不能依赖 transport 私有进度去偷做 partial reduce。

所以一个优化方向的可行性不仅由硬件决定，还由**公开接口能否表达正确同步**决定。

---

## 12. 怎样判断 cache clean 是不是瓶颈

当前每个 core 只 clean 自己写的 C rows，已经避免全局 flush。

如果 profiler/微基准显示 clean 明显：

可以研究：

```text
是否有 non-cacheable / coherent mapping 可用？
是否能让输出直接落到 SDMA 可见区域？
cache line 范围是否还可缩？
硬件是否提供更轻的 release primitive？
```

但绝不能简单删除。

先做实验验证：

```text
去 clean 是否立即出现跨卡错数？
替代 primitive 是否真正建立可见性？
```

一致性优化必须以硬件 memory model 为依据。

## 13. 怎样评价“更多融合层覆盖”

扩到更多 projection 之前，先做合同表：

| 项目 | 当前融合合同 | 新层 |
|---|---|---|
| TP | 2 | ? |
| local K | 2048 | ? |
| N | 2048 | ? |
| dtype | FP16 | ? |
| weight layout | NZ | ? |
| reduce op | SUM | ? |
| bias | 无 | ? |
| 中间非线性 | 无 | ? |
| outer reduce_results | 可关闭 | ? |

只有全都能解释，才谈复用 kernel。

不要因为 shape 一样就默认 parallel semantics 一样。

## 14. TP>2 是完全不同的设计问题

TP=2 时：

```text
每卡把自己的 partial 发给唯一 peer
然后两数相加
```

TP=4 时如果朴素做：

```text
每卡收其它 3 份
```

通信量、mail 数、arena、同步复杂度都会变化。

可能的策略包括：

```text
ring reduce
reduce-scatter + all-gather
树形
硬件 collective
多 peer MemFabric
```

因此当前 P2P 特化不要生硬外推到 TP>2。

未来扩展应该重新做通信算法选择，而不是把 peer 数从 1 改成 3。

---

## 15. 量化通信是否值得做

当前 FP16 partial：

```text
2 bytes / element
```

如果能以 INT8/FP8 传输，通信量可下降。

但代价：

```text
quantize partial
传输
dequantize / scale-aware reduce
精度风险
额外 kernel/latency
```

小 payload 时，量化固定开销可能比省下的 SDMA 时间还大。

因此要做 break-even 分析：

```text
T_quant + T_sdma_lowp + T_dequant_reduce
<
T_sdma_fp16 + T_add_fp16
```

并且必须先满足模型精度要求。

---

## 16. End-to-end 验证不能省

Micro benchmark 只回答：

```text
这个算子在这个 shape 快不快
```

最终还必须跑真实模型，因为会出现：

- Graph capture 形状变化；
- memory pressure 导致其它 cache 受影响；
- DFlash 改变 M 分布；
- 优化后 bottleneck 转移；
- 两 rank 轻微 imbalance 放大同步等待。

至少要对比：

```text
feature off
feature on q=1/2/4
normal eager
ACL Graph
normal decode
DFlash
并发场景
长稳运行
```

## 17. 每次优化建议写成“实验卡片”

模板：

```text
假设：
例如 q=2 能减少 launch 固定开销，并且 M>=1024 时不会明显降低 overlap。

依据：
profiler 显示 q=1 batch launch/wait/add 气泡占 xx%。

改动：
只改变 q，保持其它条件不变。

正确性：
随机输入和 stock MM+HCCL 比较；覆盖边界 M。

性能矩阵：
M × q × eager/graph。

成功标准：
目标 workload 加权 latency 下降 >= X%，无回归区间 > Y%。

失败后结论：
记录为什么失败，避免未来重复试。
```

这比“我感觉这样会更快”专业得多。

---

## 18. 当前值得优先验证的演进方向

不是按“必然收益”排序，而是按值得形成证据的方向列出：

### 方向 A：按真实 M 分布做 q 策略研究

先离线求出不同 M 最优 q，再评估动态 q 是否值得打破当前 fixed-context 设计。

### 方向 B：small-M 阶梯和 N-split tuning

Decode 高频区域往往更值得细抠固定开销。

### 方向 C：确认 MM/SDMA/Add 真实 overlap

如果 profiler 显示 overlap 已经很好，别继续堆复杂 pipeline；如果存在明显气泡，再研究 lookahead。

### 方向 D：减少协议固定开销

ready polling、cache maintenance、wait/add launch 等，但每项必须守住 memory/order correctness。

### 方向 E：和后继算子做更高层融合

前提是数据依赖清楚，且能减少 GM 往返而不破坏通信重叠。

### 方向 F：DFlash + MMAR 联合 shape 优化

不要只按普通 decode M 调优，要收集 speculative target verify 的实际 M 分布。

### 方向 G：内存换时间重新平衡

weight slices、arena、Graph buffers 都会占内存，优化吞吐时要同时看模型可部署容量。

## 19. 什么才算“证明当前方案已经很好”

不是说：

```text
代码看起来已经很复杂了
```

而是能拿出：

```text
1. shape histogram
2. stock vs fused timeline
3. MM/SDMA/Add overlap 证据
4. q sweep
5. small-M sweep
6. eager/graph 对比
7. 端到端吞吐/TTFT/ITL
8. memory 增量
9. correctness/稳定性
10. 已尝试但失败的替代设计
```

然后说：

> 在当前模型、310P3、TP=2、当前软件版本和目标 workload 下，主要剩余时间已经转移到 X，因此继续优化 MMAR 的边际收益约为 Y。

这才是工程意义上的“接近最优”。
