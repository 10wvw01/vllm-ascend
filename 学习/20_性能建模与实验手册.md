# 20｜性能建模与实验手册：怎样证明下一步该优化哪里

> 这一章的目标不是再列“可以优化 q、lookahead、通信格式”等方向，而是给出一套能在 310P3 实机上直接执行的实验方法：先建立时间模型，再设计最小实验矩阵，再根据 profiler 证据决定下一步。

---

## 1. 先建立一个最粗但有用的延迟模型

把一次 fused call 拆成：

```text
T_total = T_front_fixed
        + T_wave_protocol
        + T_compute
        + T_exchange
        + T_reduce
        - T_overlap
        + T_tail_or_small
        + T_graph/lifecycle
```

其中：

```text
T_front_fixed   Python/custom-op/C++ 入口固定成本
T_wave_protocol prepare/gate/ready/mail/quiet/ack
T_compute       MM
T_exchange      peer SDMA
T_reduce        local FP16 add
T_overlap       被并行隐藏掉的时间
T_tail_or_small tail copy / N-split / weight slice 等
```

优化时不要只问：

```text
某个 kernel 快了多少？
```

而要问：

```text
它是不是关键路径上的时间？
它快掉的部分有没有本来就被 overlap 隐藏？
```

如果一个 SDMA 已经完全藏在 MM 后面，再把 SDMA 快 30% 可能端到端几乎不变。

---

## 2. stock path 也要拆，不要只记录一个总时间

基线至少拆成：

```text
stock MM
HCCL AllReduce
MM->AR boundary / launch / sync
```

理想做法是同时保留两种指标：

### Layer latency

```text
一个 eligible o_proj/out_proj 从输入到 final output
```

### End-to-end

```text
Qwen 请求 TTFT / ITL / throughput
```

因为单层快 20% 不代表模型快 20%。

Amdahl 定律：

```text
Speedup_total = 1 / ((1-p) + p/Speedup_part)
```

如果目标层只占整模型 20%，目标层快 2 倍：

```text
总加速 = 1/(0.8+0.2/2)
       = 1/0.9
       ≈ 1.11x
```

所以必须同时看局部和整体。

## 3. 第一组实验：先画出 M-latency 曲线，不急着调 q

固定：

```text
TP=2
q=1
同一层 weight
FP16
feature on/off 两组
```

扫 M：

```text
1,2,4,8,15,16,17,31,32,33,63,64,65,
127,128,129,255,256,257,
384,511,512,513,
768,1023,1024,1025,
2048,4096,8192
```

为什么这些点？

因为它们正好卡在：

```text
small template stair
small-path boundary 256
batch_m boundary 256
整数 batch 与 tail
wave 上限
```

普通随机 M 会把关键不连续点淹没。

---

## 4. 对每个 M 至少记录什么

不要只记 mean latency。

建议记录：

```text
P50
P90
P99
min
mean
首次调用
warm 后 steady-state
```

并额外记录：

```text
走 small path 还是 batch path
T template
batch count
wave count
payload bytes
```

否则看到 M=257 比 M=255 突然慢，无法判断是：

```text
small->batch dispatch 跳变
还是系统噪声
```

---

## 5. 第二组实验：q=1/2/4 不应该全 M 混在一起看

q 改变：

```text
batch_m = 256,512,1024
payload = 1,2,4 MiB
```

建议分三类 M。

### A. 小 M <256

small path 开启时 q 对主 kernel 不一定直接改变 T，但会影响 scratch/runtime geometry。

这里主要确认：

```text
q 不应该意外拖累 small path
```

### B. 中等 M 256~2048

这是 q 取舍最明显区域。

例如 M=1024：

```text
q=1 -> 4 batches
q=2 -> 2 batches
q=4 -> 1 batch
```

q=1：

```text
通信启动早
协议固定开销多
```

q=4：

```text
协议开销少
但第一笔 SDMA 必须等整个 1024-row MM
几乎失去跨 batch overlap
```

### C. 大 M >8192

有多个 wave。

需要看：

```text
wave gate/ack fixed cost
q 对每 wave batch count 的影响
```

---

## 6. 怎么从时间线判断 q 该往大还是往小调

### 情况 1：MM batch 很短，signal/wait/add 固定开销很多

时间线类似：

```text
MM  MM  MM  MM
 |   |   |   |
大量短 protocol kernel
```

说明 batch 太细，考虑 q 增大。

### 情况 2：SDMA 明显暴露在 MM 之后

```text
[很长 MM0] [SDMA0]
```

而后面没有足够 MM 去遮它，说明 batch 太粗，考虑 q 减小。

### 情况 3：MM 和 SDMA 已经大面积重叠

此时不要轻易调 q，先看：

```text
add / ready clean / wave fixed cost
```

也许 q 已经接近合理区间。

## 7. 第三组实验：证明 overlap，而不是看代码猜 overlap

必须用 CANN profiler 画 device timeline。

至少标识：

```text
producer MM
SDMA request/activity
wait kernel
add kernel
quiet/credit kernel
```

希望看到：

```text
MM(n+1) 时间区间
与
SDMA(n) 时间区间
有实际重叠
```

并计算一个简单 overlap ratio：

```text
R_overlap = overlap_duration / min(T_MM_next, T_SDMA_prev)
```

例如：

```text
MM1 = 120us
SDMA0 = 100us
实际交叠 80us
```

```text
R = 80/100 = 80%
```

如果代码写了 lookahead=1 但 profiler overlap 只有 5%，就不能把设计文档里的“可重叠”当成实际收益。

---

## 8. 第四组实验：专门量固定开销

当前源码注释已经记录过几个历史实测信号：

```text
ready 32KiB 每 wave 清零 ~260us
2MiB tail memset ~0.6ms
full-B small M weight-stream floor ~150us/core
N-split small MM ~53us
```

这些数字只代表特定版本/机器上的历史证据，必须重新测。

但它们提示我们：

> 310P 这种场景，固定开销完全可能比理论 FLOPs 更重要。

建议做 isolation benchmark：

```text
prepare_wave only
producer warm/no-op
wait warm/no-op
add only
quiet/ack only
D2D scratch copy only
memset only
```

从而得到：

```text
每个机制自己的微秒成本
```

否则端到端慢时无法判断是 MM 还是协议。

---

## 9. 怎么验证 generation 优化是否真的有价值

做两个版本 A/B：

### A：当前 eager generation

```text
不清 32KiB ready
```

### B：强制每 wave clear ready

保持 M/q 其他条件相同。

重点选多 wave / 多层反复场景：

```text
M=8192
M=16384
```

看：

```text
prepare_wave latency
layer latency
```

如果差异接近历史记录数百微秒，就证明优化仍有效。

如果新版 MemFabric/CANN 已经把 clear 变成几微秒，那么可以重新评估 generation 复杂度是否值得。

这就是“历史优化也要定期重新验证”。

---

## 10. 怎么验证 tail no-memset 的收益

选 M：

```text
257
511
513
```

这些都有小 tail。

A：当前只 copy valid rows。

B：每 tail 强制 scratch memset 全 batch。

比较：

```text
tail copy/memset
总 layer latency
```

如果 B 明显更慢，说明 garbage-row localization 的优化仍然成立。

同时做 correctness：

```text
不同前一调用 M
让 scratch padded 区残留不同 stale data
```

例如序列：

```text
M=255 -> M=1 -> M=129 -> M=17
```

确认 valid output 始终与 stock reference 一致。

这叫针对“脏状态复用”的定向回归，不是只跑一个随机输入。

---

## 11. small-M threshold 应该怎么重新寻找

不要只比较：

```text
M=16 small vs batch
```

而应该扫边界：

```text
M=64..320
```

同时跑：

```text
small path on
off -> 强制 batch path
```

得到两条曲线：

```text
T_small(M)
T_batch(M)
```

交点附近才是合理 threshold 候选。

如果：

```text
T_small < T_batch 到 M=300
```

当前 ceiling=256 可能过早切回 M-split。

但如果支持 T>256 需要新 kernel template 和更大 staging，就要把工程成本一起考虑。

---

## 12. T staircase 应该怎样调

当前：

```text
16,32,64,128,256
```

对 M=129：

```text
padding ratio = 256/129 ≈ 1.98x
```

这看起来浪费很大。

可以假设加入：

```text
T=192
```

M=129 的 padding 降到：

```text
192/129 ≈ 1.49x
```

但代价：

```text
多一个 kernel symbol
多一套 warmup
binary 增长
可能 tiling 并不高效
```

所以实验应至少比较：

```text
T=128/192/256 周边真实 M
```

不要只凭 padding ratio 判断。

---

## 13. 怎么判断 add kernel 是否值得继续融合

先测：

```text
T_add / T_total
```

再看 add 是否暴露在 critical path。

如果：

```text
add 100us
但大部分和 SDMA(n+1) 重叠
```

优化 add 可能端到端收益有限。

如果：

```text
最后一个 add 暴露 100us
且下一个模型算子必须等它
```

则可以研究：

```text
reduce + next consumer
```

例如 residual/normalization 融合。

正确的判断依据是 timeline tail，而不是 add kernel 自身耗时。

## 14. “边搬边规约”怎样做成可证伪实验

先定义当前：

```text
一个 batch 1MiB
完整 SDMA 到达
wait
整 batch add
```

候选方案：把 1MiB 切成 chunk，例如：

```text
64KiB / 128KiB / 256KiB
```

对每个 chunk：

```text
signal chunk
wait chunk
reduce chunk
```

潜在收益：

```text
recv 前半块到达即可开始 vector add
```

新增成本：

```text
更多 signal
更多 mail
更多 wait kernel
更多 protocol identity
更多 cache maintenance / metadata
```

实验不要一上来改完整协议。

先测 MemFabric microbenchmark：

```text
同样总 1MiB
1×1MiB
4×256KiB
8×128KiB
16×64KiB
```

得到：

```text
T_transfer(total, chunk_size)
```

如果拆 chunk 本身就让通信时间大幅上升，边搬边规约很可能不值得。

只有 transport 对中等 chunk 仍高效，才进入下一阶段实现 overlap prototype。

## 15. lookahead depth 怎么实验

当前：

```text
L=1
```

候选：

```text
L=0: P0 W0A0 P1 W1A1
L=1: P0 P1 W0A0 P2 W1A1...
L=2: P0 P1 P2 W0A0...
```

需要记录：

```text
总 latency
MM/SDMA overlap ratio
mail wait stall
in-flight SDMA 数
arena occupancy
```

如果 L=2：

```text
overlap 没增加
wait 反而更晚
```

就没有理由增加协议复杂度。

---

## 16. 是否应该让 core0 不参与 MM，专门做 signal

这是一个很好验证的反事实实验。

当前：

```text
8 核 MM
core0 算完后兼职 signal
```

候选：

```text
7 核 MM
1 核通信协调
```

理论代价：MM 并行度下降约 12.5%。

潜在收益：core0 不必在 signal 前完成自己的 MM，可更专注协议。

但 signal 本身只是短控制动作。

所以除非 profiler 显示：

```text
core0 因承担 MM 成为 ready rendezvous 的长期 straggler
```

否则专核很可能得不偿失。

这类问题用 profiler 看 per-core completion skew，比争论架构直觉更有效。

---

## 17. 是否应该动态选择 q

当前 q 是进程级固定合同。

动态 q 的诱惑：

```text
M 小 -> q=1
M 大 -> q=2/4
```

但成本是：

```text
不同 batch_m 对应不同 arena/protocol geometry
scratch 大小变化
Graph shape/command 变化
context 不能直接复用
```

所以“动态 q”不一定意味着每调用随手切。

更现实的设计可能是：

```text
预建多个 context/profile
按 captured graph / M bucket 选择
```

但会增加内存和生命周期复杂度。

是否值得，先看 q 曲线：如果 q=1 在所有主要 M 都不差，就完全没必要动态化。

---

## 18. 通信 FP16 是否值得压成更低精度

当前每 batch payload：

```text
FP16 = 2 bytes/elem
```

如果能压到 INT8：

```text
理论 payload 减半
```

但必须新增：

```text
quantize partial
scale metadata
peer transfer
 dequant/add 或量化域 reduce
误差控制
```

而且 o_proj partial 本身可能动态范围很大，两个 rank 的 scale 若不同，不能简单 byte-wise SUM。

所以先做带宽上限判断：

```text
如果 SDMA 只占 total 10%
就算通信时间归零，总收益也 <=10%
```

没有上限收益，就不要先承担数值复杂度。

---

## 19. TP>2 是否值得扩当前 P2P 方案

先用通信量估算。

TP=2：

```text
每 rank 发 1 份 partial
收 1 份 partial
```

TP=4 如果最朴素 all-peer：

```text
每 rank 要得到另外 3 份 partial
```

通信量约增 3 倍，还要做 3-way add。

这时 ring/tree collective 算法可能更合理。

所以扩 TP 前要回答：

```text
当前 MemFabric public API 能否高效多 peer？
网络拓扑是什么？
是否要 reduce-scatter + allgather？
是否还值得自己维护，而不是回 HCCL/专用 collective？
```

TP=2 的最优解不能机械外推。

对于服务：

### Prefill

```text

```

### Decode

```text
ITL / TPOT
output tokens/s
```

### Speculative decode

```text
accepted tokens / verify round
draft latency

```

### 并发服务

```text

```

融合层 benchmark 只是解释这些 KPI 的手段，不是最终目标。

## 22. 每次优化提交最好写一张“假设卡”

例如：

```text
假设：q=2 比 q=1 更快，因为 q=1 的 protocol 固定开销过高。

证据前：
M=2048 profiler 看到每个 256-row batch 的 signal/wait/add launch 占比高。

修改：
batch_m 256 -> 512。

预期：
batch 数减半；第一笔通信启动更晚，但 MM 能覆盖。

判定：
layer P50 降低 >=X%；end-to-end ITL 不回退；correctness 通过。

结果：
...

结论：
接受/拒绝假设。
```

这样半年后再看代码，会知道一个参数为什么存在，而不是只看到“某人测过这个更快”。

## 23. 什么叫“当前方案已经够好”

不是：

```text
想不到新点子了
```

而是：

```text
关键路径上剩余可优化时间已经很小
或
下一项优化的理论上限小于复杂度/风险成本
```

比如：

```text
fused layer 300us
其中 MM 270us
所有 protocol+communication 只有 30us
```

这时通信即使全消失，也最多省 10%。

如果继续花大量工程做复杂 chunk protocol，未必是合理投入。

应该把 profiler 视角移到：

```text
Attention
MoE
sampling
Graph gaps
scheduler
```

优化的终点由系统瓶颈迁移决定。
