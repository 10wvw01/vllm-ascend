# V2 融合算子：一看就懂的图解版代码讲解

> **这份文档写给第一次接触 V2 源码的人。** 先看懂“为什么做、谁找谁、数据怎么走”，再去看具体代码。每张图下面都配大白话、源码位置与需要记住的一句话。
>
> **讲解对象**：Ascend 310P3、Qwen3.6-35B-A3B-w8a8、TP=2 的 V2 正式实现。
>
> **版本说明**：依据 `feat/310p-memfabric-public-api` 的 V2 正式源码整理（2026-10-22）。本文是“代码实际做了什么”，不是“设计文档里希望以后做什么”。诊断代码与测试脚本只作为证据线索，不参与逐行讲解。

## 先看这一张图：V2 到底干了什么？

**先用一句大白话说：原来每张卡算完自己的那一半，还要另找人把两份答案加起来；V2 让“计算、交换答案、加总答案”尽量在一次设备 Kernel 工作里做完。**

~~~mermaid
flowchart LR
    A["同一道任务拆给两张卡"] --> B0["卡0：算出半份答案 C0"]
    A --> B1["卡1：算出半份答案 C1"]
    B0 --> X["两卡交换各自的答案"]
    B1 --> X
    X --> Y["各自计算 C0 + C1"]
    Y --> R["两张卡都得到完整结果 Y"]
~~~

想象两位同事各算出一张表的一部分：A 算 C0，B 算 C1。**两个人都需要拿到 C0 和 C1，才能得出同一份最终答案 Y。** V2 的任务，就是把“各算各的 → 交换 → 合并”安排得更紧凑。

为了避免误解，还要记住三件事：

1. **两张卡仍然都在参与计算和交换。** V2 不是把 AllReduce（汇总）凭空省掉，而是用另一种方式实现它。
2. **“融合”说的是一次 AICore Kernel 启动里同时管理本地 MM、数据交换和 Add。** 并不等于没有其他 Host 初始化和后台 MemFabric 组件。
3. **“能跑通”不等于“已经更快、更稳定”。** V2 目前仍有 Eager 性能负收益、长时间运行阻塞和 Graph 没有实际执行 V2 的已归档问题。

---

## 第 1 张图：为什么原来要分两步，V2 想少做什么？

在模型的部分输出投影层中，一张卡手上的输入和权重只是整份计算的**一部分**。本地矩阵乘法，简称 **MM**，只能得到局部答案；两个局部答案还得合起来，才能成为这层真正的输出。

~~~mermaid
flowchart TB
    subgraph OLD["传统 Stock 路线"]
      direction LR
      O1["本卡 MM<br/>算出局部 C"] --> O2["HCCL AllReduce<br/>交换并汇总"] --> O3["得到完整 Y"]
    end
    subgraph NEW["V2 融合路线"]
      direction LR
      N1["进入一个 V2 Kernel"] --> N2["本卡 MM"]
      N2 --> N3["MemFabric SDMA 交换"]
      N3 --> N4["本卡 Add，得到 Y"]
    end
~~~

**图里这几个词怎么理解？**

- **MM**：矩阵乘法。就像把很多列数字按规则进行批量计算，是这层“干活”的主体。
- **AllReduce**：两张卡一起凑齐答案，并让两边都拿到合并结果。
- **HCCL**：Stock 路线中做跨卡汇总的通信方式。
- **MemFabric + SDMA**：V2 使用的“跨卡搬运通道”；SDMA 在这里主要负责**搬数据**，不是替大家做矩阵乘法。
- **Add**：拿本地和对端的两份局部答案逐项相加。此处结果使用 FP16。

**为什么要设计 V2？** 原路线的 MM 和 AllReduce 以两个阶段组织；V2 希望少一些启动与衔接成本，并尝试让下一块的计算盖住上一块的传输时间。**能否真正节省时间，要以实机测量为准。**

对应代码：`src/op_kernel/mf310p_v2_kernel.asc`（正式 Kernel），以及 `vllm_ascend/_310p/ops/memfabric_mm_ar_v2_serve.py`（决定是否走 V2）。

## 第 2 张图：V2 不只是一个 Kernel，它一共有哪几层？

这张图最重要。很多人看见 `.asc` 文件，以为“V2 全都写在这里”。其实不是：**最上面有人决定用不用它，中间有人翻译和准备，最下面才真的动手计算。**

~~~mermaid
flowchart TB
    A["① vLLM / Qwen 模型<br/>决定哪一层需要这项能力"]
    B["② Python 路由<br/>决定这一次走 V2 还是走原路线"]
    C["③ PyTorch C++ 扩展<br/>把 Tensor 变成设备调用，管好缓冲区"]
    D["④ Host 适配器<br/>建双卡共享规则、找地址、安排设备启动"]
    E["⑤ AICore Kernel<br/>8 核 MM + SDMA + Add + 同步"]
    F["⑥ MemFabric 公共能力<br/>跨卡存储和通信的基础设施"]
    A --> B --> C --> D --> E
    D -. "借用建池 / 地址交换" .-> F
    E -. "调用公共 SDMA 接口" .-> F
~~~

可以把它看成一家“**双卡协作工厂**”：

| 这一层 | 像谁？ | 主要解决什么问题？ | 代码放在哪里？ |
| --- | --- | --- | --- |
| vLLM 的模型选择 | 接单员 | 哪些模型层可以用 V2，不能误伤别的层 | `vllm_ascend/_310p/quantization/modelslim_config.py` |
| Python V2 路由 | 分单员 | 当前有多少行数据，V2 是否值得/允许接单 | `vllm_ascend/_310p/ops/memfabric_mm_ar_v2_serve.py` |
| PyTorch C++ 扩展 | 仓库管理员 | 检查 Tensor、备好输出和临时存储、绑定算子 | `src/torch_adapter/mf310p_v2_serve.cpp` |
| Host 适配器 | 调度员 | 让两张卡认得彼此、拿到正确地址、启动工作 | `src/op_host/mf310p_v2_trial_adapter.cpp` |
| AICore Kernel | 车间工人 | 真正做 MM、发/收数据、Add | `src/op_kernel/mf310p_v2_kernel.asc` |
| MemFabric | 运输公司 | 提供对称内存与跨卡 SDMA 通道 | 独立的 `memfabric_hybrid`，V2 通过公共 API 使用 |

> **代码目录里的 `src/` 简写**：上表凡是 `src/...`，都指 `csrc/_310P/memfabric_mm_ar_v2/src/...`。图中的 ①② 属于 Python 业务集成；③④⑤ 属于 V2 C++/Ascend C 工程；⑥ 是外部依赖。

## 第 3 张图：不是每一次模型计算都走 V2

**别以为“打开 V2 开关，模型就全用 V2”。** 目前它只接管符合条件的 FP16 投影层，比如目标 Qwen3.6 中的 `self_attn.o_proj` 和 `linear_attn.out_proj`。

还得满足 TP=2、固定的 2048 宽度等要求。然后，还要看本次输入的 **M**。

这里先不用怕 M：**M 就是这一回要算多少行数据。** 你可以把它想成这次收到多少行表格。

~~~mermaid
flowchart TD
    A["模型要计算一层 Linear"] --> B{"是否属于 V2 允许的投影层？"}
    B -- "否" --> S["维持该层原来的计算方式"]
    B -- "是" --> C{"现在是不是需要回退的预热过程？"}
    C -- "是" --> T["Stock：本地 MM + HCCL"]
    C -- "否" --> D{"M 是否在 2048～4096 之间？"}
    D -- "否" --> T
    D -- "是" --> V["V2：融合 MM + SDMA + Add"]
    V --> R["直接返回已汇总的结果"]
    T --> R
~~~

**举几个一眼能懂的例子：**

| 这一层的 M | 实际去哪条路？ | 为什么？ |
| ---: | --- | --- |
| 1 | Stock | 解码时行数小，目前正式 V2 Serving 不接这个区间 |
| 512 | Stock | 没达到 V2 Serving 的 2048 下限 |
| 2048 | V2 | 正好进入融合窗口 |
| 2049 | V2 | 在窗口内，但 C++ 要先把行数补成完整 chunk |
| 4096 | V2 | 当前 Serving 窗口上限 |
| 4097 | Stock | 超出 4096；不会强行多波 V2 |

**一个非常关键的小细节：为什么要关闭原来的 AllReduce？**

~~~mermaid
flowchart LR
    A["原来：MM 的结果"] --> B["上层 RowParallelLinear 再做 HCCL"]
    C["现在：V2 已经把两份结果加好了"] --> D["上层不能再加一次"]
    E["但如果改走 Stock"] --> F["Python 必须主动补一次 HCCL"]
~~~

把它想成结账：**钱已经合计过了，不能再合计一遍**。代码里将 `layer.reduce_results` 设为 `False`，就是告诉外层“这层的 TP 汇总由我负责”。但碰到 Stock 退路时，V2 Python 又必须自己补做 HCCL，保证输出的意义没有变。

对应源码，依次看：

1. `modelslim_config.py` 选中目标层；
2. `memfabric_mm_ar.py` 中 `should_enable_memfabric_mm_ar`、`configure_memfabric_mm_ar` 检查资格并避免重复汇总；
3. `memfabric_mm_ar_v2_serve.py` 中 `v2_threshold_route`、`apply` 决定这一次用哪条路。

## 第 4 张图：Python 说“用 V2”之后，数据经历了什么？

PyTorch 看到的是 `Tensor`，也就是模型里的一大块数字；Kernel 真正收到的却是显存地址、chunk 大小、Rank 信息和工作区地址。

**C++ 扩展就是“Tensor 与底层设备代码之间的翻译员”。**

~~~mermaid
flowchart TD
    A["Python 决定走 V2"] --> B["调用 torch.ops._C_ascend.memfabric_mm_ar_v2_allreduce"]
    B --> C["检查：NPU / FP16 / 形状 / Rank / Graph 状态"]
    C --> D{"这个 Worker 的 V2 池建过了吗？"}
    D -- "没有" --> E["分配固定输出槽和尾行暂存区"]
    E --> F["建立 MemFabric 池、交换地址"]
    F --> G["IB 自检 + 真实数据预热"]
    D -- "已经有了" --> H["选一个还没被占用的输出槽"]
    G --> H
    H --> I["必要时补齐行数，调用 Host 发射 Kernel"]
    I --> J["只返回真实 M 行"]
~~~

### 为什么提前准备“固定输出槽”？

可以想象一家餐厅准备了 **4 个周转餐盘**（默认数量可配置）。

模型拿着某个盘子里的结果还没用完，就不能把下一份菜倒在同一个盘子上。因此代码会检查这个输出槽是否还被别的 Tensor 引用。**没有空盘子就报错，不为了继续运行而覆盖别人正在用的数据。**

源码：`src/torch_adapter/mf310p_v2_serve.cpp` 中 `init_locked`、`reserve_slot_locked`、`memfabric_mm_ar_v2_allreduce`。

### 为什么还要“补行”？

设备 Kernel 目前只会处理完整大小的一块，例如每块 **1024 行**。但真实输入可能是 2049 行。

~~~text
真实输入 M = 2049 行；chunkRows = 1024 行

┌───────────────┐
│ 第 1 块 1024 行 │  真实输入
├───────────────┤
│ 第 2 块 1024 行 │  真实输入
├───────────────┤
│ 第 3 块：1 行   │  真实输入
│        +       │
│     1023 行补位 │  仅为了凑齐 Kernel 的完整块
└───────────────┘
        ↓
Kernel 按 3072 行计算与通信
        ↓
只把前 2049 行返回给模型
~~~

为什么选择这种办法？**让设备内核保持简单、固定，而不为每一种不规则尾行都写一套底层流程。** 补齐的那些行只是工作空间，绝不应当当作真实模型输出返回。

源码：`run_window_locked`（计算补齐行数、需要时复制数据）、`memfabric_mm_ar_v2_allreduce`（取回有效行）。

### 为什么第一次用还要“预热”？

以前实机遇到过：**协议显示没报错，第一轮输出却可能不对**。所以现在会尽量先分配长期存活的内存，建池后进行真实的双卡预热，包括输出槽、尾行和不同块深度。

这更像“工厂开机前先空转再试生产”。它只是**工程缓解措施**，不能说底层首写问题已经彻底修好。

## 第 5 张图：两张卡的数据具体放在哪里？

先介绍一个重要词：**对称内存**。

名字听起来像“两个卡看到同一块内存”，其实**不是**。每张卡都有自己的那块显存；双方事先商量好布局和远端地址，MemFabric 才知道把数据送到哪里。

~~~text
          卡 0（Rank 0）                           卡 1（Rank 1）
┌────────────────────────┐                ┌────────────────────────┐
│ C0：自己 MM 算出来的结果 │ --发送 C0-----> │ C0：收到卡 0 的结果     │
├────────────────────────┤                ├────────────────────────┤
│ C1：收到卡 1 的结果     │ <-----发送 C1-- │ C1：自己 MM 算出的结果  │
└────────────────────────┘                └────────────────────────┘
             │                                         │
             ▼                                         ▼
      本地 Add(C0,C1)                           本地 Add(C0,C1)
             │                                         │
             ▼                                         ▼
         卡 0 输出 Y                                卡 1 输出 Y
~~~

上图画的是**逻辑 C0/C1 数据区**，不代表代码中两个 Rank 的 `send_arena`、`recv_arena` 字段按同一顺序摆放。实际指针由 Host 根据 Rank 和交换后的布局分别计算。

这里最有价值的设计是：**MM 算出来的局部结果直接写入对称区里最终应该放的位置，不再先写一个普通临时区、再额外拷贝进去。** 然后 SDMA 直接把整块局部答案发给对端。

**真正决定地址的是 Host：**

~~~mermaid
flowchart LR
    A["两张卡各自建池"] --> B["双方交换对称内存的地址信息"]
    B --> C["Host 拿到最新 layout"]
    C --> D["按本卡 Rank 算 ownC、peerC、peerDst"]
    D --> E["将地址交给 Kernel"]
~~~

源码：`src/op_host/mf310p_v2_trial_adapter.cpp` 中 `mf310p_v2_trial_create`、`mf310p_v2_trial_run`。其中 `mf310p_create` 等来自 **V1 的 MemFabric 公共建池 API**：**V2 借用了运输公司的建仓库能力，不等于又跑了 V1 的计算 Kernel。**

## 第 6 张图：说是“8 核全做 MM”，那谁负责通信？

这正是 V2 容易讲错的地方：**没有专门让第 0 核只干通信、完全不参加计算。**

8 个 AI Core 全部参加本地 MM。每个核算出自己那一段，先保证自己写出的数据能够被 SDMA 读取，再告诉 Core0“我的这一段好了”。Core0 把大家的完成消息收齐后，**由它一个核统一提交本块发送任务**。

~~~mermaid
flowchart TB
    C0["Core0：计算自己那份 MM"]
    C1["Core1：计算 MM"]
    C2["Core2：计算 MM"]
    C3["Core3～7：各算自己的 MM"]
    C0 --> W["Core0 汇总：大家都算完并处理好缓存了吗？"]
    C1 --> W
    C2 --> W
    C3 --> W
    W --> S["Core0：发送 1 封整块 SDMA 邮件"]
    S --> A["收到对端数据后，放行各核 Add"]
    A --> Y["各核处理自己的输出行"]
~~~

为什么要这样安排？

- **8 核都参加 MM**：尽可能用上设备里的计算能力。
- **只让 Core0 发数据**：避免 8 核各自抢着提交通信、产生复杂协议。
- **发送之前先等其他核**：不能把一张只填写了 7/8 的表就发走。
- **各核再分别做 Add**：每人负责自己的行，不互相覆盖结果。

**还有两个关键词必须分开：**

| 关键词 | 大白话 | 解决的问题 |
| --- | --- | --- |
| `IBSet / IBWait` | 同事之间喊“我做完啦 / 我等你” | **执行顺序**：先完成，再允许下一步 |
| `CleanLines`（缓存维护） | 把各自草稿上的最新数字写到快递能拿到的地方；收件前丢掉旧草稿 | **数据新旧**：别发送旧数字，也别读到旧数字 |

> **重要**：有人喊“做完了”不等于运输系统已经看得到最新数据。所以**同步事件不能替代缓存维护**。

对应源码：`src/op_kernel/mf310p_v2_kernel_common.h` 中 `WaitReady`、`ReleaseAdd`、`WaitAddDone`、`CleanLines`；主流程在 `mf310p_v2_kernel.asc` 的 `V2TrialKernel`。

## 第 7 张图：“流水线交叠”到底怎么做到的？

不妨想象快递公司：**第一车货发出去，不必等客户收货后，工厂才开始做第二车。**

V2 可以把一次输入切成好几块。例如 M=3072、每块 1024 行，就有 **3 块**。

### 不交叠：做一块，等一块，再做下一块

~~~mermaid
flowchart LR
    A["算块0"] --> B["发/等块0"] --> C["加块0"]
    C --> D["算块1"] --> E["发/等块1"] --> F["加块1"]
    F --> G["算块2"] --> H["发/等块2"] --> I["加块2"]
~~~

### V2 Serving 用的 overlap=1：先推进下一块，再处理前一块

~~~mermaid
flowchart TB
    A["算块0"] --> B["发块0"]
    B --> C["算块1"]
    C --> D["发块1"]
    D --> E["等块0到达，做块0的 Add"]
    E --> F["算块2"]
    F --> G["发块2"]
    G --> H["等块1到达，做块1的 Add"]
    H --> I["等块2到达，做块2的 Add"]
    I --> J["整波收尾"]
~~~

对比两张图：在流水路径里，**上一块的快递已经在路上时，下一块可以继续做 MM**。这样在条件合适时就有机会省时间。

但这里**不能偷换结论**：图只是代码里的先后依赖与调度机会，**并不证明硬件上已经实现了理想的时间重叠**。如果 Core0 过早等待、SDMA 太慢、同步成本太高，实际仍可能更慢甚至阻塞。这正是后续性能归因实验要检查的问题。

**为什么最后还要单独处理块2？** 因为循环里一直在“算当前块、加上一块”，那么**最后一块没有下一轮来帮它收尾**。少了这一步就会丢掉最后一批答案。

源码：`V2TrialKernel` 里的 `overlap`、`doAdd`、循环外的“末块 Add”。

## 第 8 张图：传完了，为什么还不能立刻重复使用那块内存？

这是 V2 的**安全底线**，也是最适合在讲解时单独画出来的一张图。

**核心问题：快递送到了，不等于收件人已经把货用完了。**

设想卡 0 想把它的 C0 缓冲区拿来存下一波数据，但卡 1 可能还在读上一波收到的 C0。**写得太早，就像有人正在看报表，你突然把报表内容擦掉重写。**

~~~mermaid
sequenceDiagram
    participant R0 as 卡0
    participant R1 as 卡1
    Note over R0,R1: 双方都已执行各自的 MM、数据收发与 Add
    R0->>R0: 等本卡所有核 Add 完成
    R1->>R1: 等本卡所有核 Add 完成
    R0->>R0: quiet：确认本卡提交的发送已落地
    R1->>R1: quiet：确认本卡提交的发送已落地
    R0->>R1: DONE：我已完成本波数据消费
    R1->>R0: DONE：我已完成本波数据消费
    Note over R0,R1: 互相收到 DONE，才允许复用本波 C 区
~~~

三个动作，千万别混淆：

1. **`signal`**：我把一批货交给快递去运了。**不是**对方已经收到。
2. **`wait`**：我收到并核对对方的一批货，可以开始用它了。**不是**对方已经用完我寄出的货。
3. **`quiet + 双向 DONE`**：先确认自己的发货已经落地，再互相证明这一波已经使用完毕。之后才能安全把本波对称缓冲区拿来存下一波数据。

为什么双方都要**先发 DONE，再等 DONE**？想象两个人都说“你先告诉我你做完了”，结果谁也不先发消息，就会一直互等。

**注意**：这张时序图是逻辑顺序的简化展示。具体设备执行时，每个 Rank 的消息验证仍要检查收件地址、长度和标记；异常会触发 fail-stop，不能靠“随便收到一封邮件”就宣布成功。

源码：`V2TrialKernel` 里的 `smem_shm_sdma_signal_at`、`smem_shm_sdma_wait_at`、`smem_shm_sdma_quiet_at`，以及 `kTagDone`。

## 第 9 张图：这些代码最终是怎么变成 Python 能调用的算子？

还有个常见疑问：**“我只看到 .asc 设备代码，为什么 Python 可以调用？”**

中间有一座“桥”：**C++ PyTorch 自定义扩展**。

~~~mermaid
flowchart TB
    A["正式 Kernel 源码 .asc"] --> B["bisheng 编译为设备库 .so"]
    C["正式 Host C++ + PyTorch 适配 C++"] --> D["编入 vllm-ascend 主扩展"]
    B --> E["链接设备 Kernel 的直调符号"]
    D --> E
    E --> F["注册 torch.ops._C_ascend 的 V2 Op"]
    F --> G["Python LinearMethod 正式调用"]
~~~

这种做法叫 **Kernel 直调 + PyTorch 扩展 + vLLM 路由**：

- **Kernel 直调**：Host 直接通过导出的 launch 接口发射静态模板 Kernel。
- **PyTorch 扩展**：负责 Python Tensor 和 C++ 设备指针之间的桥接，让 Python 看到一个可调用的 Op。
- **vLLM 路由**：决定“什么时候需要调用这个 Op”，而不是让 Kernel 自己识别模型类别。

当前代码**没有走标准 ACLNN 自定义算子包的 `op_proto` / tiling 注册路线**。目录虽然也叫 `op_host/op_kernel`，但真实的编译和调用方式与 ACLNN 算子包不同。

源码：`src/CMakeLists.txt` 和仓库根目录 `cmake/memfabric_310p_v2.cmake`。正式设备文件是 `mf310p_v2_kernel.asc`；编译出的设备库是 `libmf310p_v2_trial_device.so`。

## 第 10 张图：碰到异常，会怎么处理？

为了正确性，V2 设计了一些“宁可停下来，也不继续交错计算”的防线。

~~~mermaid
flowchart TD
    A["准备执行 V2"] --> B{"输入、Rank、流、形状是否符合约定？"}
    B -- "否" --> X["直接报错"]
    B -- "是" --> C["Host 建池 / IB 自检 / 真实预热"]
    C --> D{"初始化成功？"}
    D -- "否" --> X
    D -- "是" --> E["运行 Kernel，检查设备协议"]
    E --> F{"设备是否报告协议错误？"}
    F -- "是" --> P["停止继续复用池；需要排查并协调重启"]
    F -- "否" --> G["Python 首次整块或尾块 V2 输出与 Stock 对照"]
    G --> H{"数值一致？"}
    H -- "否" --> P
    H -- "是" --> I["继续正常请求"]
~~~

这里有个重要区别：

- **协议状态没报错**：只能说明内核记录的那些通信检查没发现错误。
- **输出数值正确**：还需要拿实际结果来比较。代码对整块和尾块这两种首次融合路径分别设置了与 Stock 的比对。

过去就出现过 **`status=0`，但结果不正确** 的情况。正因为如此，V2 不能只靠一面“绿色状态灯”就宣布绝对安全。

源码：`src/torch_adapter/mf310p_v2_serve.cpp` 的状态管理、`src/op_host/mf310p_v2_trial_adapter.cpp` 的检查接口、`memfabric_mm_ar_v2_serve.py` 的首次位精确比较。

**不要上来就打开几百行 Kernel，从第一行硬啃。** 按下面顺序读，会比较容易理解上下层为什么存在。

| 阅读顺序 | 先看哪个函数 / 文件 | 看懂之后你能回答什么？ |

| ⑧ | `cmake/memfabric_310p_v2.cmake` | 代码怎么编成设备库并给 PyTorch 使用？ |

读源码时，把下列四种“地址和数据”分清就够用了：

- `x`：本卡要拿来计算的输入。
- `w`：本卡的模型权重。
- `ownC / ownPeerC`：本卡算出的半份答案、对端送来的半份答案。
- `y`：两份答案相加之后，要交还给模型的结果。

还有一个 **`rank`**：告诉程序“我现在是卡 0 还是卡 1”；**`chunkRows`** 则告诉程序“每一批货装多少行”。

## 用 1 分钟复述整条链路

> vLLM 先看这层是不是符合条件的输出投影，再看这一次数据量 M 适不适合走 V2。合适的话，Python 调用 PyTorch 自定义算子。C++ 负责准备固定的输出位置、做好双卡通信初始化和必要的预热。Host 把两张卡的内存地址告诉 Kernel。Kernel 让 8 个核一起完成本地矩阵乘法，由 Core0 统一提交跨卡数据搬运；收到对端结果之后，各核再把两份结果加起来。整波完成时，两张卡互相确认“上一批已经用完”，然后才能安全使用同一片内存处理下一批。最后 C++ 把真正需要的 M 行结果交给 Python，外层就不再重复执行 HCCL。

如果这段能说清楚，**V2 的主体架构就已经掌握了**。

## 最后一定要讲清楚：目前哪些是做到了，哪些还没有？

| 问题 | 目前应该怎么讲？ |
| --- | --- |
| “V2 是不是一个 Kernel 完成 MM+通信+Add？” | **是，正式 T0 计算路径如此组织**；但还存在池初始化、后台通信基础设施和 PyTorch/Host 调度。 |
| “8 个核里是不是有 1 个专职通信？” | **不是。Core0 同样参与 MM/Add，只是它统一负责通信 signal/wait。** |
| “V2 是否所有 M 都能运行？” | **不是。当前正式 Serving 只路由 2048～4096；其他 M 走 Stock。** T0 的独立试验上限不能直接当 Serving 能力。 |
| “Graph 已经能完整使用 V2？” | **不能这样说。** 当前 FULL_DECODE_ONLY 的 Graph 小 M 走 Stock；已归档实验里 Graph 没有真正调用 V2。 |
| “融合后性能一定提升？” | **不能这样说。** 原有 Eager 性能负收益、长稳问题和专项取证尚需解决。 |
| “协议检查没报错就一定数值正确？” | **不是。** 代码还有首次输出与 Stock 位精确比对，历史上发生过协议状态正常而结果错误。 |
| “这次文档改写会影响 Kernel 行为吗？” | **不会。** 本次只重写讲解文档，不调整正式计算、通信和构建逻辑。 |

### 最后记住这 5 句话

1. **Python 决定用不用 V2；C++ 负责准备；Kernel 负责真正算。**
2. **两卡先各算一半，再交换，再各自加出完整答案。**
3. **8 核都干计算，Core0 兼职负责统一发送和收信。**
4. **通知做完不等于数据已经可见；送达不等于对端已经用完。**
5. **V2 的目标是更快，但正确性、稳定性和性能要分别拿实机证据说话。**
