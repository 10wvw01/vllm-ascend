## 1. 先用一句话说清 V2

V2 在 310P3、TP=2 的特定 FP16 RowParallelLinear 上，把各 Rank 本地矩阵乘法、MemFabric SDMA 交换局部结果、向量相加收敛为**一个 AICore Kernel launch**；通过 C++ Host 管理两卡对称内存与跨 Rank 协议，再包装成 PyTorch `torch.ops._C_ascend.memfabric_mm_ar_v2_allreduce`，最后经 vLLM 的模型量化方法选择器将合格的投影层路由过来。**不是**把所有 `Linear` 替换，也**不是**把 HCCL 库实现直接嵌入 Kernel。

数学合同（每 Rank）：

```text
Rank0: X0[M,2048] × W0[2048,2048] = C0[M,2048]   (FP16)
Rank1: X1[M,2048] × W1[2048,2048] = C1[M,2048]   (FP16)
两个 Rank 最终各得到 Y = C0 + C1
```

权重采用适配的 NZ 表示、输出 ND；通信媒介是两 Rank 的 MemFabric 对称内存，不是 HCCL AllReduce。关键并发约束是**每块 8 核均完成并清理本地 C 后才发信号；本端收到对端 C 后才能 Add；一波结束且双端确认已消费，才允许覆盖工作区**。

## 3. 一次真实请求怎样穿过 6 个边界

```text
Qwen3.6 构建 eligible RowParallelLinear
  ↓ ModelSlimQuantConfig310.get_quant_method / should_enable_memfabric_mm_ar
  ↓ MemFabricMmArV2LinearMethod310.process_weights_after_loading
  ↓ configure_memfabric_mm_ar: reduce_results=False（避免上层重复 TP 规约）
  ↓ MemFabricMmArV2LinearMethod310.apply
      ├─ 非合格 / warmup / M<2048 / M>4096: 原生 MM + HCCL
      └─ 2048≤M≤4096: torch.ops._C_ascend.memfabric_mm_ar_v2_allreduce
          ↓ C++ 参数检查、状态锁、按需首次建池
          ↓ 输出槽 lease / 尾块 stage / 首波预热
          ↓ mf310p_v2_trial_run 计算 rank 映射 + launch 参数
          ↓ mf310p_v2_trial_launch_async
          ↓ V2TrialKernel<tilingROWS, ROWS> 8-core 单 kernel
              MM → clean → IB fan-in → signal → wait → IB release
              → clean recv → Add → IB done → quiet → DONE 互证
          ↑ 输出槽 narrow 回实际 M
      ↑ Python 第一次按“整块/尾块”形状分别与 Stock 位精确比对
      ↑ 已融合分支直接返回，不能再做 HCCL
```

这里有**两道不同的正确性边界**：设备 `status` 表示低层协议错误（设备侧异步错误需同步后才能可靠检查）；Python 的首次输出 Stock bit-exact 比对捕获 `status=0` 但结果错误的情况。后者**不等于**已解决所有后续冷启动、长稳或 Graph 风险。

## 4. 路由合同，读代码先盯住“谁负责 TP 规约”

`modelslim_config.py` 对符合模型选择的未量化层建立子类；真实资格由 `should_enable_memfabric_mm_ar` 控制：模型文本类型、层前缀和混合 layer type、TP=2、分片输入 2048、输出 2048、FP16、非额外量化方法等；只对目标 `self_attn.o_proj` 和 `linear_attn.out_proj` 生效。

`configure_memfabric_mm_ar` 将 `layer.reduce_results` 从 `True` 改为 `False`：**这一动作很关键**。普通 RowParallelLinear 会在 LinearMethod 计算后执行常规 HCCL；V2 的输出已经完成 TP 汇总，因此如果不关闭这一层归约就会“算两次”。V2 Python 代码在走 Stock 退路时**自己**补做 `tensor_model_parallel_all_reduce(super().apply(...))`，保持输出语义相同。

V2 正式 Serving 实际路由：

- `M < 2048`、`M > 4096`、profile/dummy fallback：Stock 本地 MM + HCCL。
- `2048 ≤ M ≤ 4096` 且符合资格：V2 融合（此路径的 `overlap=1`）。
- `chunk_rows` 只接受 256/512/1024。用户 Forward 非 chunk 整倍数由 C++ 常驻 `input_stage` 补齐，输出裁剪为原 M。
- 仅允许不处于 active capture 的大 M 路径；既有 `FULL_DECODE_ONLY` 的小 M Graph 本质上是 Stock 路径，**当前不能据此断言 Graph 捕获了 V2**。

## 5. PyTorch 扩展：为什么有“常驻输出槽”和“首用预热”

`TORCH_LIBRARY_FRAGMENT` 声明 Op schema，`torch::kPrivateUse1` 绑定 NPU 侧 C++ 实现。实现先检查设备、FP16、形状/连续性、TP rank、chunk、M、capture 状态，再锁定 `V2ServeState`：该对象持有 MemFabric handle、执行 stream、输出槽池、输入暂存区和 poisoned 标志。

初始化遵守**先分配 Tensor/固定生命周期，再创建 MemFabric 池**的顺序：这是历史 MTE3 首次输出异常的工程规避措施，而非器件根因证明。输出槽通过 `StorageImpl` 引用计数判断是否仍被模型持有；若全部在途则 fail-stop，不覆盖未被消费的结果。尾行 `copy_` 被安排在同一 NPU stream 上，避免因独立 Host memcpy 路径观察到过时输入。建池、IB probe、逐输出槽真实两卡通信预热、尾块预热、深度扫查都在首次服务前完成；每次普通请求不做逐波 Host 同步。

限制：`V2ServeState` 的生命周期是 Worker 级，不是请求级；跨 stream 并发、异常后继续复用池都未开放。异常进入 `poisoned`，需要重启两 Rank。退出时同步和回收；不把“局部捕获成功”当成可靠性证据。

## 6. Host API：对称池如何接到 Kernel 指针

`mf310p_v2_trial_create` 通过既有 V1 **公共** `mf310p_create`、`mf310p_control_barrier`、`mf310p_exchange_geometry` 建立 TP2 对称内存和对端几何。**交换完成后才**调用 `mf310p_get_layout` 读取最终布局；另外分配清零 IB GM workspace、错误状态和自检缓冲。调用方需先设置正确设备/ACL context。

`mf310p_v2_trial_run` 检查 handle、IB 探针完成、输入、chunk 对齐、窗口以及 overlap；按 rank 将 `send_arena/recv_arena` 映射为“本 Rank MM 写区 / 对端消息接收区”。它发射的参数包括发送目的 GVA 和**预期接收地址**；设备必须在 wait 后校验 dst/len/imm，不能仅因收到任意邮件就 Add。使用长期存活的池，单个 wave 不复用某块的偏移。

首个 kernel 符号的 `enable=0` 预热与首次真实 launch、新输出地址的 `aclrtSynchronizeDevice` 是**当前代码存在的代价和风险**，有可能造成双 Rank 时间偏斜，不能解释成“优化后的同步”。状态先 `aclrtMemsetAsync` 清零，再向指定 stream 入队；`run` 返回不表示已完成。明确同步点和错误复核由上层执行。

## 7. Kernel：8 核计算、1 核发信、两侧核内规约

`V2TrialKernel` 根据 `CHUNK` 静态 tiling 处理每个 chunk 的 `CHUNK/8` 行，8 核均执行 MM；`GetBlockIdx()==0` 并非独占通信核，**也参与本地 MM 和 Add**。每个核 MM 直接写本地对称区中的 ND 结果，`CleanLines` 维护 SDMA 可见性；`WaitReady` 完成 7→1 IB fan-in 后，Core0 使用 MemFabric 公共 `smem_shm_sdma_signal_at` 发送整块。返回值仅代表提交成功，不等同于对端已读。

对于 `overlap=0`：当前 chunk 的 `wait`、验信、核间 `ReleaseAdd`、收件区缓存失效、Add 紧随其后；对于 `overlap=1`：当前 chunk 完成信号后，处理前一个 chunk 的收件与 Add，最后在循环外处理末块。这是**单 Kernel 内部**的串行/流水两条路线，而不是两次 Kernel launch。每核向量队列分批把 C0/C1 读入 UB，FP16 Add 后直接写 Y。

所有 Add 结束后由 `WaitAddDone` 汇合；Core0 `quiet` 确保自己已提交的 SDMA 发送落地，接着向对端控制槽投递 8B DONE，并等待对端 DONE。只有这组协议共同成立，双方才可认为本波数据已被对端消费，安全复用对称缓冲。Kernel 失败调用 `CheckOrTrap` 写状态并终止，后续不能继续使用污染的池。

`mf310p_v2_kernel_common.h` 的 `kIBReady/kIBDone/kIBReleaseBase` 对应不同事件消费方向；**一份 IB 事件不允许被多个接收核当作广播重复消费**。`CleanLines` 与 IB 分别处理 cache 可见性和核间时序，二者不可混为一谈。静态 `V2_TILING(256/512/1024)` 不等于支持任意 M。

## 8. 构建和诊断为什么分离

根 `cmake/memfabric_310p_v2.cmake` 确保 310P3 目标、MemFabric 公共头和 bisheng 可用，将正式 `.asc` 构建为 `libmf310p_v2_trial_device.so`，并把 Host/Serving C++ 编译进主扩展。设备直调导出 `mf310p_v2_trial_launch_async`，Host 调用它，PyTorch 暴露更高层的 Tensor API：三个符号边界**不是**同一 ABI。

`VLLM_ASCEND_310P_V2_BUILD_DIAGNOSTICS=OFF` 是**正式最小构建**，不会编译 `*_diagnostics.*`；默认 ON 为保持历史验证 ABI。唯一例外：正式 Serving 仍依赖 IB 安全自检，相关入口留在正式内核/Host，不应误删。这套工程**没有** ACLNN tiling 注册、`op_proto` 算子包入口，目录虽然借用了 CANN `op_host/op_kernel` 分层，实际仍是 bisheng/ACL stream Kernel 直调。

## 9. 讲解顺序与边界提醒

推荐当面讲解沿着以下阅读路径展开：`modelslim_config.py`（为何选择）→ `memfabric_mm_ar_v2_serve.py`（选择后何时融合）→ `mf310p_v2_serve.cpp`（PyTorch Tensor/Pool）→ `mf310p_v2_trial_adapter.cpp`（Rank 地址/ABI）→ `mf310p_v2_kernel_common.h`（事件/缓存）→ `mf310p_v2_kernel.asc`（逐 chunk 时序）→ `cmake/memfabric_310p_v2.cmake`（构建）。

必须区分三类结论：

1. **源码事实**：固定 TP2/FP16/2048 宽、8 核、Core0 唯一 data signal、Serving 融合 M=2048..4096、Graph active capture 禁用。
2. **历史实机观察**：部分 T0/G3 功能测试与目录重构回归曾通过；存在 Eager 负收益、长稳阻塞、Graph 未真正执行 V2 的独立问题，见 `V2_REFACTOR_REGRESSION_20261019.md` 与 `ARCHIVE_20261019_G3.md`。
3. **尚待证实**：V2 Graph 生产可用、负收益根因消除、长期稳定、跨场景性能普遍领先。注释和本文均不能代替 310P3 实机证明。
