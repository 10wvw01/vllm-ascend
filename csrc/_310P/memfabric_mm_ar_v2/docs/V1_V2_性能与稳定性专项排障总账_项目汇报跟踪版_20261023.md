## 一、给项目负责人的 1 分钟结论

**项目已经验证“融合可以算对”，但还没证明“真实业务更快、长时间不挂”。目前不具备生产合入条件。**

- **功能**：V2 在限定输入范围内的 TP2 位精确、40 个目标层的 Eager 路由已跑通，这是成果。
- **性能**：真实 Qwen Eager 中，V2 对比原生 Stock 的吞吐三次为 **-3.51%、-4.53%、+2.12%**，中位为 **-3.51%**，TTFT 三次均变差。已经找到约 **0.63ms/目标层**的融合 Kernel 额外成本，正在做单变量优化。
- **选型**：**V1 和 V2 谁更值得继续投入，还没有最终选定。** 虽然同口径单层测试中 V2 略快于 V1，真实 vLLM Eager **缺少 V1 的同场数据**，必须补测。
- **稳定性**：V2 偶发双 Rank 507014 挂死，已找到它卡在“等对端通信完成通知”的具体位置；也看到目标通知槽保留旧值。**高度怀疑 MemFabric 交付/可见性链路，但仍未证明具体是哪条 SQE、哪段代码或硬件行为导致。**
- **眼前任务**：OpenCode D4 验证 Tile2048 能否提速；准备 Stock/V1/V2 三方 Eager 公平选型；与 MemFabric 团队一起继续排查那封“没被看到的邮件”。

## 二、我们到底做到了哪里？

### 2.1 研发路线图（沿着问题推进，不是零散调参）

**先证明能用**（基础 IB、MM、SDMA、Add、输出槽和尾块正确）
→ **真实模型发现变慢**（G3 Stock/V2 Eager）
→ **找到慢在哪儿**（40 个目标站点、单 Kernel 约多 0.63ms）
→ **排除误判**（contiguous 拷贝非额外开销、设备内部计时不能用）
→ **找出可保留的设计**（4 Chunk 的 overlap=1 交叠确实有用）
→ **确认测量可靠**（D1-A Profiler ON/OFF 对照）
→ **动正式代码做第一项优化**（D2/D3：Add Tile 1024→2048）
→ **D4 等实机验收**（尚无结果）  
→ **最后回到真实业务，决定 V1/V2/Stock 路线**。

稳定性是另一条并行链：

**Eager 长压挂死**
→ G1-A 复现签名
→ G1-B 排查 Host 队列、Epoch
→ G1-C 找到 AI Core 第一个等待位置
→ G1-D 抓到具体 seq、接收 ARR 槽和旧 stamp
→ **下一步按目标请求追踪 3 条 SQE 与接收端可见性**
→ 才能做单变量修复、关闭诊断、多轮 Gate E 长稳。

## 三、最重要的路线决策：先决定重点优化 V1 还是 V2

### 3.1 现有数字为何还不能选赢家？

| 相同单层测试：M=4096，越低越好 | Stock | V1 | V2 overlap |
|---|---:|---:|---:|
| 10/17 逐调用同步耗时 | 3.156ms | 2.808ms | 2.738ms |

单层 V2 比 V1 约快 0.07ms，但真实 vLLM 可以把多个算子异步排队；单层的优势完全可能在真实模型里消失。

| 真实 vLLM Eager：50 条请求、输入4096、输出2048、并发10 | Stock | V1 | V2 |
|---|---|---|---|
| 同条件模型数据 | 已有基线 | **缺失，待测** | 吞吐相对 Stock：-3.51%、-4.53%、+2.12%；TTFT三组均劣化 |

**决策项 SEL-01：** 让 OpenCode 用 **Stock→V1→V2→V2→V1→Stock** 的独立进程交叉顺序完成同配置 Eager 对照。先证明 V1/V2 真的打中相同目标层、数值正确、SO/KVER 版本一致，再比较吞吐、TTFT、TPOT/ITL、尾部、失败数和日志。

最终只允许三种结果：

1. **V1 更快且安全条件可满足**：优先把精力转去 V1；既有 V2 优化保留作为备选。
2. **V2 更快且安全条件可满足**：继续推进 V2。
3. **都不够快或都不稳定**：先保留 Stock，并分别补安全和性能证据。

**没有同场 V1 数据就不选边。** D4 是 V2 局部优化，不替代 SEL-01 选型。

## 四、性能专项：为什么当前 V2 变慢？下一步具体改什么？

可以把每个目标层想象成“先做矩阵乘法，再让两张卡交换半成品并相加”。正常 Stock 的 MM 和 HCCL 在真实模型里配合得比单层微基准好，所以 V2 省掉了一次 Kernel Launch，也未必能省掉真正的等待。

| 可能慢的地方 | 当前判断 | 下一步 |
|---|---|---|
| Python 或输入 contiguous 多拷贝 | **已排除该目标路径额外拷贝的误判** | 不再为它专门改代码 |
| MM 算数本身 | MAC 活动量基本符合 4 个 Chunk；但 Tiling/访存还没有彻底排除 | 作为后续候选，不先动 |
| SDMA 到达、IB、Scalar 等待 | MTE2/Scalar 活动偏高，**只能确认相关，不能按计数器当阶段精确耗时** | MemFabric/Kernel 两侧进一步拆证据 |
| CleanLines 逐条 Cache Line 维护 | 有大量操作，**是否能省未知** | 先证明缓存可见性不受影响再优化 |
| 4 Chunk 交叠 | **交叠有用**：D1-A 裸 Event 对串行约省 0.39～0.59ms | 保留 4 Chunk、overlap=1 |
| Add 规约循环 | D3 已把每 Core、M4096 循环数从1024降为512；额外使用6KiB UB | D4 验证 BiSheng/UB/位精确/ABBA，**性能未知** |
| 偶发 74ms/23～45ms 长尾 | 有历史真实样本，D1-A 未复现；与 Gate E 不可直接画等号 | 保留异常数据，后续独立判别 |

### D4 当前里程碑

## 五、稳定性专项：Gate E 挂死排到哪一步？该谁处理？

**一口气说清楚：** 两张卡交换数据，好比把快递投到指定柜子。V2 的 0 号核一直守着目标柜子，等“送到了”的单据；快递系统的调度侧说单子已经处理，柜子里却还是上一圈的旧单据。两张卡后续任务互相等，最终 507014。

### 真实故障 D1R4 最关键的四组数字

| 现场 | rank0 / dev0 | rank1 / dev1 |
|---|---:|---:|
| V2 代际和状态 | gen1730，Core0 阶段50 | gen1730，Core0 阶段50 |
| ARR 是“已消费游标”，不是发货量 | 8632 | 8634 |
| 实际盯的柜子 / 应有单号 | **440 / 8633** | **442 / 8635** |
| 柜内读出的旧单号 | **7609** | **7611** |

**重点纠错**：旧 G1-D 报告曾把等待槽误说成 **439/441**（head-1）。已逐行核对 MemFabric `wait_at`，真正等待的是 **440/442**（head 本位）。移交团队必须附上更正文档，别让对方排错槽。

已掌握：故障时 Host 请求环已消费，SQ 队列看起来空、Epoch 正常；V2 进入 `smem_shm_sdma_wait_at` 却始终没有返回，没走到邮件校验。  
**仍缺：** 对应那封邮件的**数据拷贝、stamp 写入、mail 写入**这三条 SQE 是否逐条正确组装、提交、被设备执行，以及接收侧最终是否可见。

### 责任分工：先把问题交给最有能力调查的人，不先定罪

**MemFabric 团队应牵头处理跨卡交付链路**，因为要追查的是它所实现的请求消费、SQE 和完成邮件；**V2 团队负责证明调用接口、地址生命周期、单 Core signal 和缓存使用没有越过合同**。现有证据足以启动联合排障，但**还不足以宣布“MemFabric 软件 BUG 已经实锤、V2 完全无责”**。

交接包至少要提供：故障复现命令与固定负载、双 Rank `serve.log`、设备 plog、D1R4 gen/seq/ARR 快照、Host/Epoch/SQ 采样、两仓库源码 SHA 和实际 Host/插件/Device/KVER 二进制哈希、故障/健康对照、脱敏原始日志清单及 SHA256。**逐 SQE 执行/完成证据是下一轮补采项，不可以凭空补齐。**

**Gate E P0 关闭门槛**：捕到可反证的根因 → 只改一处 → 回归位精确/冷池/双 Rank → 去掉诊断埋点再跑原 Gate E 持续 Prefill/Decode 多轮长稳。一次不挂不叫修复。
