## 二、我们到底做到了哪里？

### 2.1 研发路线图（沿着问题推进，不是零散调参）

**先证明能用**（基础 IB、MM、SDMA、Add、输出槽和尾块正确）
→ **真实模型发现变慢**（G3 Stock/V2 Eager）
→ **找到慢在哪儿**（40 个目标站点、单 Kernel 约多 0.63ms）
→ **排除误判**（contiguous 拷贝非额外开销、设备内部计时不能用）
→ **找出可保留的设计**（4 Chunk 的 overlap=1 交叠确实有用）
→ **确认测量可靠**（D1-A Profiler ON/OFF 对照）
→ **动正式代码做第一项优化**（D2/D3：Add Tile 1024→2048）
→ **D4 实机完成：单算子+6.26%，Eager成功会话+1.86%；Gate E类挂死仍出现**  
→ **最后回到真实业务，决定 V1/V2/Stock 路线**。

稳定性是另一条并行链：

**Eager 长压挂死**
→ G1-A 复现签名
→ G1-B 排查 Host 队列、Epoch
→ G1-C 找到 AI Core 第一个等待位置
→ G1-D 抓到具体 seq、接收 ARR 槽和旧 stamp
→ **下一步按目标请求追踪 3 条 SQE 与接收端可见性**
→ 才能做单变量修复、关闭诊断、多轮 Gate E 长稳。

## 四、性能专项：为什么当前 V2 变慢？下一步具体改什么？

可以把每个目标层想象成“先做矩阵乘法，再让两张卡交换半成品并相加”。正常 Stock 的 MM 和 HCCL 在真实模型里配合得比单层微基准好，所以 V2 省掉了一次 Kernel Launch，也未必能省掉真正的等待。

| 可能慢的地方 | 当前判断 | 下一步 |
|---|---|---|
| Python 或输入 contiguous 多拷贝 | **已排除该目标路径额外拷贝的误判** | 不再为它专门改代码 |
| MM 算数本身 | MAC 活动量基本符合 4 个 Chunk；但 Tiling/访存还没有彻底排除 | 作为后续候选，不先动 |
| SDMA 到达、IB、Scalar 等待 | MTE2/Scalar 活动偏高，**只能确认相关，不能按计数器当阶段精确耗时** | MemFabric/Kernel 两侧进一步拆证据 |
| CleanLines 逐条 Cache Line 维护 | 有大量操作，**是否能省未知** | 先证明缓存可见性不受影响再优化 |
| 4 Chunk 交叠 | **交叠有用**：D1-A 裸 Event 对串行约省 0.39～0.59ms | 保留 4 Chunk、overlap=1 |
| Add 规约循环 | D3 已把每 Core、M4096 循环数从1024降为512；额外使用6KiB UB | D4 编译/正确性/ABBA已通过（+6.26%）；Eager成功会话吞吐+1.86%，**稳定性仍NO-GO** |
| 偶发 74ms/23～45ms 长尾 | 有历史真实样本，D1-A 未复现；与 Gate E 不可直接画等号 | 保留异常数据，后续独立判别 |

## 五、稳定性专项：Gate E 挂死排到哪一步？该谁处理？

**一口气说清楚：** 两张卡交换数据，好比把快递投到指定柜子。V2 的 0 号核一直守着目标柜子，等“送到了”的单据；快递系统的调度侧说单子已经处理，柜子里却还是上一圈的旧单据。两张卡后续任务互相等，最终 507014。

### 真实故障 D1R4 最关键的四组数字

| 现场 | rank0 / dev0 | rank1 / dev1 |
|---|---:|---:|
| V2 代际和状态 | gen1730，Core0 阶段50 | gen1730，Core0 阶段50 |
| ARR 是“已消费游标”，不是发货量 | 8632 | 8634 |
| 实际盯的柜子 / 应有单号 | **440 / 8633** | **442 / 8635** |
| 柜内读出的旧单号 | **7609** | **7611** |

**重点纠错**：旧 G1-D 报告曾把等待槽误说成 **439/441**（head-1）。已逐行核对 MemFabric `wait_at`，真正等待的是 **440/442**（head 本位）。移交团队必须附上更正文档，别让对方排错槽。

已掌握：故障时 Host 请求环已消费，SQ 队列看起来空、Epoch 正常；V2 进入 `smem_shm_sdma_wait_at` 却始终没有返回，没走到邮件校验。  
**仍缺：** 对应那封邮件的**数据拷贝、stamp 写入、mail 写入**这三条 SQE 是否逐条正确组装、提交、被设备执行，以及接收侧最终是否可见。

### 责任分工：先把问题交给最有能力调查的人，不先定罪

**MemFabric 团队应牵头处理跨卡交付链路**，因为要追查的是它所实现的请求消费、SQE 和完成邮件；**V2 团队负责证明调用接口、地址生命周期、单 Core signal 和缓存使用没有越过合同**。现有证据足以启动联合排障，但**还不足以宣布“MemFabric 软件 BUG 已经实锤、V2 完全无责”**。

交接包至少要提供：故障复现命令与固定负载、双 Rank `serve.log`、设备 plog、D1R4 gen/seq/ARR 快照、Host/Epoch/SQ 采样、两仓库源码 SHA 和实际 Host/插件/Device/KVER 二进制哈希、故障/健康对照、脱敏原始日志清单及 SHA256。**逐 SQE 执行/完成证据是下一轮补采项，不可以凭空补齐。**

**Gate E P0 关闭门槛**：捕到可反证的根因 → 只改一处 → 回归位精确/冷池/双 Rank → 去掉诊断埋点再跑原 Gate E 持续 Prefill/Decode 多轮长稳。一次不挂不叫修复。

**更关键的判断：长输出2048时，Prefill-only很难撑起5%的整模型改善。** SEL-01有效样本整场约2177秒，而当前40层Prefill融合核按设备时间估算只占约5.11秒，直达预算不足0.25%；说明接下来需要在固定4096输入/2048输出/TP2/batch10/Eager中优先查明**Decode高频耗时**，而非继续叠加低收益的Prefill微优化。该预算是近似估算，不能冒充因果实验。

### 最新性能方向：从只优化Prefill转向先找Decode真正热点（2026-10-24）

SEL-01说明：在输入4096/输出2048/TP2/batch10 Eager场景中，Stock吞吐45.98tok/s、V2 Tile2048为46.49tok/s（+1.12%，不稳定）；主要生成时间用于长Decode。**因此C线改为先做Decode成本取证，再决定正式算子优化点**，C3 CleanLines保持源码候选但暂缓完整模型长压。

初步从源码发现需要优先测量：40层MoE路由/两次Grouped MatMul、30层GDN的卷积/循环状态与PyTorch门控、多达10层PagedAttention、TP2原生HCCL及量化/Host提交。**这些是出现频率高，不代表已经证明耗时高。** C4已提交双Rank Profiler CSV轻量分类与严格窗口校验工具，[查看C4研究与执行方案](https://github.com/10wvw01/vllm-ascend/blob/perf/310p-c4-decode-cost-attribution-20261024/csrc/_310P/memfabric_mm_ar_v2/docs/C4_QWEN36_DECODE_HIGH_VALUE_ATTRIBUTION_20261024.md)。设备数据尚未采集；总账已完成任务数不变。

### 2026-10-24 决议：回归MM+MemFabric AllReduce，F2优先、F1并行

此前将C线扩大到全模型MoE/GDN/Attention属于研究目标偏移；**C4通用全模型优化暂停**。仅聚焦310P3单卡双Die上 `MM + MemFabric SDMA + FP16 Add/AllReduce` 这条算子关键路径。Stock保持默认，已验证的D4 Tile2048保留；C3 CleanLines +1.70%且不稳定，NO-GO并存档。

- **F2 大M（优先上机）**：在D4基线上，用同一设备SO扫描M2048/4096、Chunk256/512/1024、Overlap0/1，双Rank配对Event、逐次位精确和fail-closed；独立报告将确定是否有值得正式编码的交叠与调度候选。[F2方案与脚本](https://github.com/10wvw01/vllm-ascend/blob/perf/310p-f2-mm-sdma-overlap-sweep-20261024/csrc/_310P/memfabric_mm_ar_v2/docs/F2_MM_SDMA_ADD_OVERLAP_PERF_PLAN_20261024.md)。
- **F1 小M（并行研发、随后上机）**：对Decode目标M=10及M1/8/16/32/64，复用T1小MN-split和Stock原生MM+HCCL基准，先确定固定协议成本和分核空间；初轮仅可选型筛查、不能称已经打赢Stock。[F1方案与脚本](https://github.com/10wvw01/vllm-ascend/blob/perf/310p-f1-smallm-fixed-cost-20261024/csrc/_310P/memfabric_mm_ar_v2/docs/F1_SMALLM_MM_AR_FIXED_COST_PLAN_20261024.md)。

OpenCode现场独占同一卡对**先F2后F1**，均需先做CPU合同测试、锁定KVER11/Host/Device SO哈希并保全原始数据。用户规定的真实模型三方评测永远固定**输入4096、输出2048、TP=2、batch上限10、Eager**，不混用D4输出512。两线均**尚未执行本轮实机**，因此路线收益依然UNKNOWN；不改变42项中23项完成的原始统计。
