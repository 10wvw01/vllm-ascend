## 静态审查第二轮（协议因果与工程门禁）

- [x] **唯一邮件消费者**：`E4WaitPacketAndRelease`中Core1..7直接`IBWait`并返回，只有Core0调用`smem_shm_sdma_wait_at`。
- [x] **按包分区**：tag part0精确释放Core1..3，tag part1精确释放Core4..7；Core0本核Add必须等待两封mail到齐。两条4MiB信件可以交换到达顺序；重复、过期、越界、状态错误均进入`CheckOrTrap`。Core0每组对每个其他Core事件仅投递一次。
- [x] **组间事件复用前进性推导**：Core0完成组`g`的两封mail后才处理自己Add`g`；其他核完成对应Add`g`后才进入下一轮`MM(g+1)→ReadyTree(g+1)`。Core0要获得下一轮全8核Ready，先前每核对应Release已经被消费（一个核不可能跳过Add而跨组），降低了跨组复用未消费IB事件的风险。该推理**不能替代真实310P3 IB协议/时序证明**。
- [x] **最终Buffer生命周期**：整轮`WaitAddDone`等待7个工作核完成，Core0之后才`quiet`并跨Rank互发/互等DONE；未绕过KVER11、缓存可见性或错误处理。
- [x] **内存预算**：Vector 3路队列UB需求分别12/24/48KiB，`TOTAL_UB_SIZE > kUBForIB + VECTOR_UB`断言。**Matmul剩余Workspace是否能支持48KiB向量队列须以真实BiSheng编译及设备Smoke判定**。
- [x] **连续M**：纯CPU`e4_shape_plan.py`定义[2048,4096]全2049个M、合法2048/1024/512/256组、最多4096总行及≤4MiB包；未知性能或L3未证一律返回Stock。**变长组设备Kernel/Host实机仍未实现**。
- [x] **纯CPU协议模型**：`e4_packet_protocol.py`与新增UT覆盖两包乱序、重复、坏状态、过期tag、dst/len错误、跨组Release事件计数，具备可复测的模拟证据；其结果不等于设备IB硬件行为已验证。
- [x] **评估可信度**：14场`stock,e1,e3g,e4t2,e4t4,e4t8,e4p,e4p,e4t8,e4t4,e4t2,e3g,e1,stock`；每形状每rank100有效样本，同序号pair max、两场漂移5%，保留p99，不从独立臂p50做设备阶段耗时差值。

## 未解决事项和本轮不做的范围

1. **E4-P的真正可回收时长未知**：Core0仍等两封mail才执行自己的Add，所以Packet0的提前放行可能只能隐藏Core1..3的一部分工作。需实机确定，不可用源码假设速度。
2. **M2048缺乏组间交叠依然存在**：E4-P只优化consumer，不提前Producer发送Packet0；若M2048 Screen没有收益，下一轮才重排core-ownership或设计1024+1024混合。
3. **任意M自适应尚非设备事实**：规划器覆盖M∈[2048,4096]不意味着Kernel支持分组/尾块。要在后续独立阶段加入真正按2048+1024/512/256组序执行的设备Kernel、宿主padding-copy与严格Stock完整链对照，不用纯CPU规划器冒充真实性能。
4. **E3归档中的原始失败PLog/build日志仍待补**：主线已保存52份原始机测数据但原PR缺失的异常摘录不能由E4静态审查重建。
