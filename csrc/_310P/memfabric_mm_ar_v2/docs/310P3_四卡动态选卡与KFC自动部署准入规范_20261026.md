# 310P3 四卡动态选卡、故障换卡与 MemFabric KFC 自动部署准入规范

> **生效日期：**2026-10-26；**决策：**ADR-014；**范围：**V2 MM+MemFabric AllReduce 的全部310P3实机实验，单卡双Die TP=2。  
> **现场事实：**服务器共有**4张物理310P3卡**，但每张的实时健康/占用和设备号必须每次现场复核，不能从历史枚举结果推断。  
> **主要依据：**[2026-10-23 换卡及 KFC 实机记录](MEMFABRIC_310P_KFC_DEPLOY_AND_DEVICE_PIVOT_20261023.md)；[MemFabric 310P使用指南](https://github.com/10wvw01/memfabric_hybrid/blob/wgm-dev-310p/docs/310p/使用指南.md)和[设备侧部署档案](https://github.com/10wvw01/memfabric_hybrid/blob/wgm-dev-310p/docs/310p/部署档案.md)。部署行为依据所选软件版本的现场日志与SHA，不从文档泛化为所有平台事实。

## 一、每次实验都必须先从4张卡中择优选卡

1. **全面只读巡检**：OpenCode/运维先列出4张物理卡、每卡两个Die的物理号与同卡拓扑、两个Die和MCU的健康状态、业务/进程/显存占用、租户权限和端口冲突；以 `npu-smi info` 及相关进程/拓扑只读证据为基础。不得预设固定卡或误将两个不同物理卡的Die拼成TP2。
2. **选择健康且独占的完整卡**：仅当两Die均健康、MCU无未处理Alarm、无外部租户和不可解释驱动故障时，才可作为候选。历史 `0,1`、`2,3`、`4,5`、`6,7` 只是当时服务器上的设备编号示例，必须再次按板卡实际拓扑确认。
3. **G0期间异常可换卡**：某卡告警、业务占用或通信状态异常，标记该卡 `EXCLUDED`、保存只读快照并尝试下一张空闲健康卡；每换一次卡都**重新建立G0**。旧43520的dev6/7曾出现Die7/MCU Alarm，未提供解除告警的新证据前不要重新选为健康卡。四卡均不合格则全机 `G0_NO_GO`。
4. **运行中异常先停机取证，不自动巡回跑坏四卡**：发生507014/507899、AICore timeout、位精确错误、IB卡住、KFC 0x2a/部署失败或设备管理无响应，先STOP当前会话，保全Rank0/Rank1日志、设备信息、错误现场，分析是否系统性软件/版本问题；**只有明确授权后**才能在另一健康卡开启新实验。禁止测试脚本自动切卡/重试掩盖原故障。
5. **每组A/B/ABBA都固定在一张卡**：Stock MM+HCCL AR与V2 MM+MemFabric AR必须同一物理卡、同一对Die、同一SO/KVER/环境完成独立A/B；ABBA中途绝不换卡。换卡=全新run_id/单独G0/独立预热与统计，不能拿A卡Stock与B卡V2计算加速比。

## 二、换卡的DeviceID必须同时满足逻辑/物理映射

2026-10-23的实机证据表明：

- MemFabric初始化以进程 `aclrtGetDevice()` 得到的**逻辑DeviceID**为入口；`SdmaOrchestrator` 按逻辑编号奇偶判断Die语义。设定 `ASCEND_RT_VISIBLE_DEVICES=<经现场确认的物理Die0>,<物理Die1>` 后，进程逻辑号通常为0/1，**不能将逻辑号直接当作物理号**。所选顺序必须验证和当次Rank/Die奇偶匹配。
- 在当时310P3+CANN 9.1实际探针里，`aclrtMallocPhysical` 需要**逻辑号**，但 `aclrtMemSetAccess` 需要**物理号**。非0/1重映射（当时 `2,3` / `6,7`）如果把逻辑号误用于SetAccess会报 **507899**。
- 旧问题通过修复版MemFabric Host库的 `HybmPhysicalDeviceIdOf(logicDevId)` 在三个 `AclrtMemSetAccess` 位置转换为物理号：meta区、own段、imported对端段；**不要改MallocPhysical的逻辑号**。历史修复SO SHA256以 `1dc46d7d` 开头，旧版恢复库以 `88d39285` 开头，两个前缀仅是历史定位线索，不能代替U1冻结的**完整SHA**。
- Host SO存在系统 `lib64` 与Python `site-packages/memfabric_hybrid/lib` 两套可能装载路径，必须分别核对完整SHA、真实进程装载来源与本次设备SO/KVER版本。部署需事先备份+许可+回滚，不因换卡自动覆盖系统SO；也不得为了通过G0降低SHA校验。

## 三、KFC何时部署？正常只需要自动部署，不需提前给四张卡手工装

KFC是设备侧执行/管理通道；MemFabric需要设备上的AICPU SDMA编排Kernel。**经过G0并单独批准短Smoke后**，目标双Die首次建池/初始化会触发MemFabric的自动部署流程：

`LoadOrchestratorKernel → RunDeployHelper → orch_deploy_helper → KFC test -f → 若不存在则CUST迁移与KFC复制 → 检查文件尺寸/符号 → TryLoadKernel`。

本项目v11历史的典型目标文件为 `/usr/lib64/aicpu_kernels/0/aicpu_kernels_device/libmf_sdma_orch_v11.so`，入口符号 `HybmSdmaOrchEpoch`。路径中的 `0` 是设备侧搜索目录结构，**不是宿主物理卡0**。部署按目标Die分别验证是否可用：2026-10-23 dev6首次缺失被自动部署、dev7同时报告已经在位。旧手动部署诊断文档中另有“同卡共享设备OS”的叙述，不能据此跳过新版目标每个Die的实际加载证据。

**KFC判定注意：**

- `KFC sync=507018` 只有出现在“缺失探测→自动部署成功→核验完整→Kernel正常加载”的**完整链路**里才是可容忍的中间状态；独立507018、AICPU `0x2a`、helper失败均STOP。
- 以前遗留过 `MF_SDMA_ORCH_DEPLOY_HELPER=<立即返回rc=3的伪脚本>`，会谎称新Die已部署而触发 `0x2a`。换卡G0先检查环境中是否有未经审核的覆盖helper；不要把伪成功当作KFC已部署。
- v11正式服务默认epoch有限纪（`MF_SDMA_ORCH_EPOCH_BUDGET_S`未设置/0→15s）；诊断常驻模式值 `4294967295` 不可用于Serving/正式性能对比。KVER11/launch JSON/Host库版本必须匹配，不能只凭文件名判断。
- **只读G0阶段绝不运行手工KFC部署、`mini_kfc`删除/复制、建池初始化或Torch Kernel。** 只有健康独占、身份SHA、恢复方案、明确执行授权均通过，才允许在短Smoke里观察自动KFC链并验证每个Die的加载。

## 四、换卡后重新核验的最小G0清单

| 门槛 | 必须记录的证据 | 不满足的动作 |
|---|---|---|
| 四卡只读健康/占用 | 4卡列表、物理卡标识、每Die及MCU状态、显存/进程/租户、选卡/排除理由 | 换空闲健康卡或NO-GO |
| 同卡拓扑与映射 | 当前卡两Die物理号；Rank0/Rank1→逻辑0/1→物理Die对应；可见设备列表顺序 | STOP，修正映射后重新G0 |
| 非identity DeviceID修复 | 双Host SO完整SHA、`HybmPhysicalDeviceIdOf`修复的已审版本、真实装载路径 | 未修复/版本不符STOP，禁止盲测507899 |
| 当前D4设备SO与KVER11 | 完整SHA、实际设备加载/注册来源、插件import真实路径 | 不匹配STOP，不伪造SHA |
| KFC自动部署前置 | 没有假helper/违规常驻模式；G0不对KFC已部署做假判定 | 未获授权不触发部署；首次Smoke内确认 |
| 安全与回滚 | 设备独占、HCCL端口/ROCE隔离、备份SO与恢复路径/权限、异常停测措施 | 不满足STOP |
| 短Smoke KFC验证 | 各Die helper状态、v11文件/符号核验、编排核可加载、无0x2a/507014/507899 | FAIL/STOP并保留故障现场 |

已有 `a1_g0_readonly.py` **只能校验一个选定设备对的部分文件/工具状态**；它不负责枚举四卡、证明拓扑、判定自动部署完成，也永远不会签发G0批准。不得据此宣称选卡或KFC已完成。

## 五、与A1通信等待优化的关联

`四卡巡检 → 选择健康空闲同卡双Die → G0只读身份校验 → 人工批准M2048短Smoke（初始化自动KFC） → KFC/正确性/状态PASS → 同卡Stock/V2 Screen → 单独HCCL跨流审计 → 经授权Confirm/ABBA`。

设备卡故障不应无期限阻塞主线A：**只在卡级健康异常且另有健康空闲卡时按本原则换卡**。但不能把507014/IB等运行错误直接当作坏卡而在四张卡上轮流复现，避免将系统性协议故障扩散。

每次回传报告新增 `card_selection.json` 或同等表格：四卡候选、排除卡、选中卡、Rank物理映射、KFC各Die状态、版本身份、换卡次数及理由。跨卡结果只能作为独立设备差异对比，不能拼成同一A/B的速率收益。
