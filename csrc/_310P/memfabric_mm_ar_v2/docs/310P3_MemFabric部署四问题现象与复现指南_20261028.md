# 310P3 MemFabric 部署四问题现象与复现指南

> **日期**：2026-10-28；**性质**：历史问题现象归档 + 已授权诊断会话的复现参考。
> **范围**：2026-10-20 至 10-23 期间 MemFabric Host 库 / KFC 部署与运行环境的四个问题（三层拼装版本溯源、伪 helper 残留致 AICPU 0x2a、非 0/1 设备 507899、常驻模式 serve 507017），以及后两个问题的复现方法。
> **边界声明**：本文档不构成新实机实验、SO 替换、建池/KFC 运行的自动许可；所有复现步骤均须先按 [ADR-014](DECISIONS.md) 与[四卡准入规范](310P3_四卡动态选卡与KFC自动部署准入规范_20261026.md)取得授权、完成 G0 并选定健康独占同卡双 Die。文中复现均为最小化诊断动作，测后必须清理环境变量与临时装载路径。

## 一、四个问题的现象

### 1.1 三层拼装版本溯源（10/20）

**现象**：对 `/usr/local/memfabric_hybrid` 做只读审计时发现，`version.info` 声明 CommitId `2f59dedb`，但实际运行的核心库 `libmf_hybm_core.so` 是 fix 分支热替换产物；安装呈三层拼装：

| 层 | 时间 | 产物 | SHA256 前缀 | 来源 |
|---|---|---|---|---|
| ① .run 包安装 | 10-12 15:14–15:19 | `lib64/libmf_smem.so` 等除 core.so 外全部 | `daec2332`（smem） | `2f59dedb` 源码构建 |
| ② 部署助手 | 10-19 01:40:44 | `lib64/orch_deploy_helper` | `849f93c0` | 主树 `tools/aicpu_kernel_deploy/` 构建（源码 == `fix-310p-kfc-deploy-helper` 已提交版本） |
| ③ 核心库热替换 | 10-19 02:15:07 | `lib64/libmf_hybm_core.so`（site-packages 同步替换） | `88d39285` | mf-fix 工作树构建（`fix-310p-kfc-deploy-helper` `131ee5ff` 等价源码） |

另发现：KVER11 launch json（`libmf_sdma_orch_v11.json`）引用 `kernelSo=libmf_sdma_orch_v11.so`，该文件名在安装目录无对应实体（实际 .so 仍叫 `libmf_sdma_orch.so`）。

**根因**：安装产物多来源叠加，元数据不反映真实装载；CMake 版本化 json 规则与实际部署名未对齐。

**处置**：装载身份必须以**完整 SHA256 + 进程 `/proc/<pid>/maps`** 审计，不能只信 version.info、文件名或 Git commit。证据见[版本溯源报告](310P3_版本溯源与资产保全报告_20261020.md)。

### 1.2 伪 helper 残留致 AICPU 0x2a（10/23）

**现象**：换到 dev6/7 后，首次 launch `HybmSdmaOrchEpoch` 报 **AICPU errorCode=0x2a**（编排核二进制找不到）。

**根因**：wedge 时期为绕过 helper 退出挂死遗留的 `MF_SDMA_ORCH_DEPLOY_HELPER=<立即返回 rc=3 的脚本>` 谎报 kernel 在位（该捷径仅在 dev0/1 三重验证过合法），换卡后环境失效，库信以为真跳过部署。

**处置**：移除伪 helper 后自动部署链恢复（dev6 从零部署成功）。教训固化为规范：任何“假定在位”的快捷路径必须随环境失效立即移除；G0 先检查环境中是否有未经审核的覆盖 helper。

### 1.3 非 0/1 设备 507899（10/23）

**现象**：设 `ASCEND_RT_VISIBLE_DEVICES=6,7` 换卡后，建池在 meta 区授权处（`hybm_gva.cpp:82`）报 **507899（DRV_INTERNAL_ERROR）**，建池失败。

**根因**（2×2 探针实证）：CANN VMM API 命名空间分裂——

| API | location.id=逻辑号 | location.id=物理号 |
|---|---|---|
| `aclrtMallocPhysical` | **OK** | 失败 107001 |
| `aclrtMemSetAccess` | 失败 **507899** | **OK** |

identity 映射（不设 VISIBLE 或 `=0,1`）下逻辑号=物理号，二者恒等从未暴露；非零起点可见列表把逻辑号误喂 SetAccess 必现 507899。

**修复**：Host 库补丁 `HybmPhysicalDeviceIdOf(logicDevId)` 按 CANN 同款语义解析 `ASCEND_RT_VISIBLE_DEVICES`，在三个 `AclrtMemSetAccess` 位点（meta 区 / own 段 / imported 对端段）换算物理号；`MallocPhysical` 保持逻辑号不动。修复 SO SHA 前缀 `1dc46d7d`；dev6/7 验证建池 + 8 形状双 Rank 位精确全 PASS。

### 1.4 常驻模式 serve 必死 507017（10/23）

**现象**：AICPU 编排核以常驻哨兵模式（`MF_SDMA_ORCH_EPOCH_BUDGET_S=4294967295`）运行时，serve 进程以 **507017** 死亡。

**根因**：torch_npu 分配器内部会触发 `AclrtSynchronizeDevice`（全设备、全流、无豁免），常驻 AICPU 任务永不自退，必然阻塞该同步。

**修复**：v11 起（`2f59dedb`，2026-10-12）默认 **epoch 有限纪**——未设/0/非法预算→15s，内核按 host 心跳时钟（100ms/跳）到时自退，监督线程 ~100ms 轮询后重拉；每次同步最坏等待 ≤1.5×预算。换纪有 ~100–300ms 间隙（请求环排队、零丢失设计）。常驻值仅限诊断，禁止用于 Serving 与正式性能对比。

## 二、后两个问题的复现方法

### 2.1 复现 507899

#### 方法 A：最小 VMM 探针（推荐，不触碰 MemFabric/KFC）

探针源码留存于服务器 `/tmp/opencode/d4/vmm_probe.c`（临时目录，可能被清理，全文备份如下）：

```c
/* D4 环境探针：验证 aclrt VMM API 的 location.id 命名空间（逻辑 vs 物理）。
 * 用法: vmm_probe <setaccess_location_id> [malloc_location_id]
 * 在 ASCEND_RT_VISIBLE_DEVICES=2,3、当前设备=逻辑0(物理2) 下运行矩阵：
 *   (malloc_id, set_id) ∈ {0,2}²，对照 VISIBLE=0,1 的 (0,0)。 */
#include <stdio.h>
#include <stdlib.h>
#include "acl/acl_rt.h"

int main(int argc, char **argv)
{
    if (argc < 2) { printf("usage: %s <set_id> [malloc_id]\n", argv[0]); return 2; }
    int set_id = atoi(argv[1]);
    int malloc_id = (argc > 2) ? atoi(argv[2]) : 0;
    aclError r = aclInit(0);
    if (r && r != 100000 /* already inited */) { printf("aclInit ret=%d\n", (int)r); return 2; }
    r = aclrtSetDevice(0);
    if (r) { printf("SetDevice(0) ret=%d\n", (int)r); return 2; }

    void *va = 0;
    const size_t sz = 2UL * 1024 * 1024;
    r = aclrtReserveMemAddress(&va, sz, 0, 0, 0);
    printf("reserve ret=%d va=%p\n", (int)r, va);
    if (r) return 1;

    aclrtPhysicalMemProp prop = {};
    prop.handleType = ACL_MEM_HANDLE_TYPE_NONE;
    prop.allocationType = ACL_MEM_ALLOCATION_TYPE_PINNED;
    prop.memAttr = ACL_MEM_P2P_HUGE;
    prop.location.id = (uint32_t)malloc_id;
    prop.location.type = ACL_MEM_LOCATION_TYPE_DEVICE;
    aclrtDrvMemHandle h = 0;
    r = aclrtMallocPhysical(&h, sz, &prop, 0);
    printf("malloc_physical(id=%d) ret=%d\n", malloc_id, (int)r);
    if (r) { aclrtReleaseMemAddress(va); return 1; }

    r = aclrtMapMem(va, sz, 0, h, 0);
    printf("map ret=%d\n", (int)r);
    if (r) { aclrtFreePhysical(h); aclrtReleaseMemAddress(va); return 1; }

    aclrtMemAccessDesc acc = {};
    acc.flags = ACL_RT_MEM_ACCESS_FLAGS_READWRITE;
    acc.location.id = (uint32_t)set_id;
    acc.location.type = ACL_MEM_LOCATION_TYPE_DEVICE;
    r = aclrtMemSetAccess(va, sz, &acc, 1);
    printf("set_access(id=%d) ret=%d %s\n", set_id, (int)r, r == 0 ? "OK" : "FAIL");

    (void)aclrtUnmapMem(va);
    (void)aclrtFreePhysical(h);
    (void)aclrtReleaseMemAddress(va);
    (void)aclrtResetDevice(0);
    return r != 0;
}
```

参考编译命令（按现场 CANN 安装路径调整）：

```bash
gcc vmm_probe.c -I/usr/local/Ascend/cann-9.1.0/include \
  -L/usr/local/Ascend/cann-9.1.0/lib64 -lascend_cl -o vmm_probe
```

运行（前置：授权会话 + 健康独占卡 + G0；探针只使用当前逻辑设备）：

```bash
export ASCEND_RT_VISIBLE_DEVICES=2,3   # 或 6,7；逻辑0=物理2
./vmm_probe 0 0
./vmm_probe 2 2
./vmm_probe 2 0
```

预期结果矩阵：

| 命令 | MallocPhysical id | SetAccess id | 预期 | 含义 |
|---|---|---|---|---|
| `./vmm_probe 0 0` | 0（逻辑） | 0（逻辑） | malloc OK；**SetAccess ret=507899** | 未修复库的行为，**复现点** |
| `./vmm_probe 2 2` | 2（物理） | 2（物理） | **malloc ret=107001** | MallocPhysical 要求逻辑号 |
| `./vmm_probe 2 0` | 0（逻辑） | 2（物理） | 全 OK | 补丁后的正确组合 |

对照臂：`ASCEND_RT_VISIBLE_DEVICES=0,1`（identity）下 `./vmm_probe 0 0` 全 OK——这正是该缺陷在 identity 场景从未暴露的原因。探针只申请并释放 2MB 物理内存，无持久副作用。

#### 方法 B：全链复现（旧 Host SO + 非 0/1 映射 + 首次建池）

1. 取未修复 Host SO：`/tmp/opencode/d4/c0/backup_hostso_20261023T153335/libmf_hybm_core.so.orig`（SHA256 前缀 `88d39285`）；
2. 以**私有目录 + `LD_LIBRARY_PATH`** 装载旧库（A1-R1 纪律），不覆盖系统 `lib64` 或 site-packages 任一路径；进程启动后用 `/proc/<pid>/maps` 确认实际装载来源就是该私有旧库；
3. `export ASCEND_RT_VISIBLE_DEVICES=6,7`（以现场核实的健康独占卡为准）；
4. 运行任一首次建池入口（如授权后的 `mf310p_v2_trial_create` 或 M2048 短 Smoke）。

**预期**：建池在 meta 区授权处报 507899 失败。**对照臂**：同一会话改装载修复版 SO（`1dc46d7d`）重复相同步骤 → 建池成功，即构成差分证明。

### 2.2 复现 507017（常驻模式 serve 必死）

前置：授权会话、健康独占同卡双 Die、G0 通过、当前 v11 栈（默认 epoch 模式）。

```bash
# 常驻哨兵模式（仅本次诊断，测后必须清除）：
export MF_SDMA_ORCH_EPOCH_BUDGET_S=4294967295
# fused serve 参考环境（G3 同款，按当次 G0 冻结值调整）：
export VLLM_ASCEND_310P_ENABLE_MEMFABRIC_MM_AR=1
export VLLM_ASCEND_310P_MEMFABRIC_MM_AR_V2_SERVE=1
export VLLM_ASCEND_310P_MEMFABRIC_V2_CHUNK_ROWS=1024
export VLLM_ASCEND_310P_MEMFABRIC_V2_OUTPUT_SLOTS=4
export VLLM_ASCEND_310P_MEMFABRIC_STORE_URL=tcp://127.0.0.1:8581
export MF_SDMA_ORCH_JSON=<run包>/libmf_sdma_orch_v11.json
# 启动 TP=2 fused serve 并加载模型
```

**预期**：建池成功、编排核以常驻模式驻留后，torch_npu 分配器触发的全设备同步被永久阻塞，serve 进程以 507017 死亡（历史实测死亡码）。**对照臂**：清除 `MF_SDMA_ORCH_EPOCH_BUDGET_S`（恢复默认 15s epoch 有限纪）后同负载 serve 健康。

## 三、治理与安全约束（每次复现均适用）

1. **授权与 G0**：两类复现均为实机动作，须按 [ADR-014](DECISIONS.md) 与[四卡准入规范](310P3_四卡动态选卡与KFC自动部署准入规范_20261026.md)取得明确授权、四卡只读巡检选定健康独占同卡双 Die、完成 G0 身份核验后方可执行；
2. **STOP 纪律**：出现预期之外的 507014/507899/AICPU 0x2a/挂死，原地 STOP 保全双 Rank 日志与设备状态，禁止自动换卡轮测四卡；
3. **常驻模式仅限诊断**：`4294967295` 不得进入任何正式性能对比，复现结束立即清除该环境变量；
4. **SO 一律私有装载**：旧/新 SO 对比走私有 `LD_LIBRARY_PATH` + `/proc/<pid>/maps` 取证，不覆盖共享安装路径，测后无需回滚系统；
5. **禁用伪 helper**：不得设置任何 `MF_SDMA_ORCH_DEPLOY_HELPER` 覆盖；
6. **产物清理**：`vmm_probe` 二进制与临时 SO 目录测后可清理，探针源码已全文备份于本文档 §2.1。
