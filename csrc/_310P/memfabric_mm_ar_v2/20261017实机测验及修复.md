全部位精确通过：

## 3. 修复的缺陷

### BUG #1 探针结果区多核并发写丢写（G0 阶段）
- 现象：8 核并发 volatile 写同一 32B 结果缓冲，读回时随机缺核。
- 根因：dav-2002 各 AI Core L1 不互通，同 cache line 并发写在回写时互相覆盖。
- 修复：每核 64B 独占槽 + 写后 `DataCacheCleanAndInvalid`（设备侧 `WriteResultSlot`；host 侧 kProbeResultBytes=512、按 64B 步长校验）。与 V1 ready cell 同款纪律。
- 回归：G0 三 chunk × 双 reps 全部稳定通过。

### BUG #2 adapter 在 exchange_geometry 之前调用 get_layout（G1 阶段）
- 现象：`mf310p_v2_trial_run` 拒绝调用（rc=-1），expected_recv_base/expected_credit_dst 为 0。
- 根因：创建流程顺序错误，布局尚未与对端交换就取布局。
- 修复：镜像 V1 runtime——先 `mf310p_exchange_geometry` 再 `mf310p_get_layout`。
- 回归：地址转储与 V1 逐项一致，G1 起不再出现 rc=-1。

### BUG #3 建池后新分配输出缓冲的 MTE3 首写静默丢弃（G1/G2 阶段，核心问题）
- 现象：进程内**首次**对该符号的完整发射，y 全零（预填标记值 -777 原样保留，证明 MTE3 写被丢弃而非写零）；内核其余部分全部正常——status 标量见证、MM 的 GM 写（ownC 逐核标量快照非零且正确）、IB 握手、SDMA mail 校验、quiet、DONE 握手、Add 循环计数（64 tile）全落地，RC=0，无任何错误码。第二次发射起完全正确。
- 排除过程（全部实测）：非 Add 抢跑 MM 的竞态（快照证明数据全程在 GM）；非 IB 失效（G0 通过且分阶段 diag 全对）；非 16 参编组问题（argcount 探针全槽位验证）；非内核代码缺陷（V1 逐字移植版与循环复刻版在同一进程均正确）；流级同步、SDMA memset、额外内核发射（enable=0 或 enable=1）**均不能**修复；torch 侧 `stream.sync()` 或建池前预分配 y 则可修复。
- 根因（实测定性）：MemFabric 建池的后台流（AICPU orchestrator/地址映射）与本计算流不同流；建池**之后**由 torch 分配的新输出缓冲，其页面在设备侧映射完成前被 AICore MTE3 写访问会静默丢弃。流级 sync 等不到这些后台流；**全设备同步（aclrtSynchronizeDevice）可等待其完成**。池内存（建池时映射）与建池前分配的缓冲不受影响。
- 修复：`mf310p_v2_trial_run` 内部跟踪 y 指针（`warmed_y`），y 首次出现或更换时先 `aclrtSynchronizeDevice()` 再发射。输出缓冲实际很少更换，稳态零额外开销。`MF310P_V2_NOWARMUP=1` 可关闭（仅测试用）。
- 回归：G1 全矩阵（含 1000 次复用）与 G2 全 18 配置通过；同一 y 的后续调用不触发同步（计时中位数无退化）。

### BUG #4（harness）NZ 格式常量错误
- torch_npu 的 FRACTAL_NZ 枚举是 29 而非 3；早期"x@w 伪转置"全部由此引起。修复后 V1 producer 逐字移植版与 V1 原库均位精确，确认内核本身无恙。

### 设备环境问题（非本代码缺陷，记录备查）
- dev0/1 的 KFC system() 通道损坏（fork 失败 ret=4294967295，plog "KFC system run failed"；dev2 正常），导致 orchestrator 建池 auto-deploy 失败。绕过：预占 /tmp/mf_kfc_<pid>_{0..15}.json 使 LoadKfcChannel 返回 BM_FILE_NOT_ACCESS(-5) → 走 assume pre-deployed 分支（v11 内核确在设备上，V1 bench 验证数据面健康）。npu-smi set 容器内不可用，无法复位设备。
- 现象级备注：V1 的"launch every symbol twice"纪律与本 BUG #3 的首启危害同源（首次访问新映射页面的写路径不可靠）。

## 4. 测试方法论要点
- 双 rank torchrun harness；g0/g1/g2/stock/diag 五模式；4 输入变体（不同 seed）；每次调用后 status=0 断言 + 位精确校验；复用循环逐次校验。
- 分级隔离 diag 0–7 是定位 BUG #3 的关键手段：各级均位精确而生产路径首启失败，把嫌疑收敛到"launch 环境"而非"内核逻辑"。
- 判别实验：y 预填标记值（区分"没写"与"写零"）、每核 64B 快照（排除竞态）、地址/参数逐项转储对比（排除参数差异）。

## 5. 遗留风险与未验证项
- kernel 固定 8 核、整 chunk、整波 8192 行：tail、动态 M、graph replay、多 wave 未验证。
- BUG #3 的硅级机制为实测定性（全设备同步可治愈），未获得设备侧官方解释；若未来 CANN/MemFabric 版本变更，预热策略需复测。
- `MF310P_V2_NOWARMUP` 为 C 层 getenv 测试钩子（实验代码，未纳入 vllm_ascend/envs.py 体系）。
- 小 M（≤1024）性能劣于 stock，接入模型路由前需按层形状评估。
- 诊断脚手架（diag 0–7、addresses/ib_addr/status_addr/status_words、argcount 探针、V2DiagLoopKernel）保留在设备库中，仅测试可达，不影响生产路径。
