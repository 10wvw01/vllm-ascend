# 公共非阻塞收件接口需求（提交 MemFabric 团队）

## 背景与目标

310P3 TP2 的 MM + inlineReduce 融合 Kernel 由 Core0 唯一调用现有 SDMA
signal/wait/quiet。计算核独立产出，Core0 必须在 MM 子调用边界处理已到的
READY、ADD 完成及 Gather 完成，再推进其他就绪片段。目前 wait_at 在无邮件时阻塞，
使一个未到邮件阻止本地计算与其他就绪工作继续。希望增加公共非阻塞收件接口，
不让业务 Kernel 访问私有环/SQE/游标，也不以超短超时模拟轮询。
当前方案 A 继续使用原接口，此需求仅支持增强方案 B，不阻塞 A 交付。

## 建议接口及必须约定的语义

建议提供设备侧 `try_wait_at(res, &mail)`（名称及类型以团队公共 API 规范为准），
返回三个可区分的结果：`MAIL_READY`、`EMPTY`、`ERROR`。

- `EMPTY`：当前没有可消费的已完成邮件；执行有界检查后立即返回，不自旋等待、不睡眠、
  不产生 TIMEOUT，不消费或跳过未完成的队头，不误推进消费者 head。
- `MAIL_READY`：仅消费 FIFO 中下一封完整且有效的邮件，填充与现有 wait_at 一致的
  status/dst/len/imm。每封恰好消费一次，不跳过较早未完成项；不要求按标签选择或乱序摘取。
- `ERROR`：溢出、会话故障、协议或传输错误必须可与 EMPTY 区分，保留现有错误信息。
  错误不能伪装为无邮件；接口不重发数据任务，尤其不得重试不确定的 ADD。
- 完成语义应与 wait_at 完全一致，请明确 ADD 完成邮件是否保证发送源已读完、
  目的写/累加已完成，以及接收 Core 后续提交 Gather 所需的排序保证。
  请同时明确所需的调用方 DCCI/fence；不要求接口隐式替业务清理全部数据缓存。
- 明确该调用是否维护接收 credit/消费游标、是否影响发送队列持续进展。
  在只调用 try_wait 与 signal、暂不调用 wait 的合法循环中，不应因遗漏必需进展而停滞。
  如维护有额外限制，请给出公开合同及有界成本。
- 延续单消费者模型。应允许同一 Core 在合法边界交替调用 wait_at 与 try_wait_at，
  共用同一消费位置；不需要多个核并发收件，也不需要后台线程或新通信引擎。

## 验收与交付请求

请在 Atlas 310P3 / dav-2002 和双方锁定的 CANN/SDK 上提供公共头、实现、最小示例及
版本/ABI说明，并覆盖：连续空轮询不改变 head/credit；空转非空；延迟完成不早读；
多邮件 FIFO 和恰好一次消费；环回绕；双 Rank 偏斜；COPY 与 FP16 ADD 完成；
try/wait 交替；溢出及错误不变成 EMPTY。请给出空调用及有邮件调用的有界成本/测量条件。
若现有实现不能保证上述某项，请直接标注限制，便于我们决定是否启用方案 B。
