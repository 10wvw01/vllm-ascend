# 310P3 o_proj 计算通信协作优化方案

> 状态：目标设计（待实现）
>
> 基线：`feat/310p-memfabric-public-api` @ `381cb22ccdb0444c917b49c486c78a18f6552994`
>
> 目标模型：`Eco-Tech/Qwen3.6-35B-A3B-w8a8`
>
> 目标硬件：Ascend 310P3 / dav-2002，单物理卡双 die，TP=2

本文只描述下一版计算/通信协作终态。MemFabric 仍作为外部黑盒，只使用 public
`smem_shm_sdma_signal/wait/quiet`，不依赖其私有 ring/SQE/orchestrator 布局。

## 1. 当前实现需要解决的问题

当前代码为：

```text
block0      : communication coordinator
block1..7   : 7 个独立 MM worker
每个 worker: usedCoreNum = 1
MM(chunk) -> clean -> ready -> block0 signal
全部 chunk 完成 -> quiet/wait all -> add whole wave -> credit
```

当前自定义 MatMul 静态 tiling 为 `128/128/128`，并通过小 `tile_m` chunk
制造 overlap。实机已经证明该路径能形成 MM/SDMA overlap，但大 MM 被拆成多个独立
单核 GEMM，计算效率损失明显。

目标机原生 o_proj profiler 基线为：

```text
baseM = 256
baseN = 256
baseK = 64
```

因此下一版原则是：**通信适应原生 MM，而不是为了通信破坏 MM。**

## 2. 最终设计原则

固定以下约束：

1. **8 个 AI Core 全部参与 MM**，取消专职 communication core。
2. **core0 同时参与 MM，并固定作为唯一 data signal owner**；不做多 producer
   `signal()`。
3. MM 计算基本粒度与原生 profiler 对齐：
   `baseM=256, baseN=256, baseK=64`。
4. 通信/规约 batch 必须由整数个 `baseM` stripe 组成，不按固定字节数硬编码。
5. 一个 batch 的本地 partial 完成并 cache 可见后，core0 立即异步
   `signal()`；下一 batch MM 不等待前一 batch SDMA。
6. peer batch 到达后立即规约该 batch，不再等待整个 wave 的所有数据到齐。
7. 第一版继续保留现有 **wave-level fixed credit**，不引入 batch-level credit，
   避免扩大协议复杂度。
8. Graph、fail-stop、strict mail validation、生命周期与 public-API 边界保持不变。

## 3. 统一 batch 定义

计算 stripe：

```text
COMPUTE_STRIPE_M = baseM = 256
```

通信和规约使用同一 batch 边界：

```text
BATCH_BASEM_COUNT = q
BATCH_M           = baseM * q
BATCH_BYTES       = BATCH_M * N * sizeof(FP16)

q 建议候选：1 / 2 / 4
默认首测：q = 2
```

当前 N=2048、FP16 时：

| q | BATCH_M | BATCH_BYTES |
|---|---:|---:|
| 1 | 256 | 1 MiB |
| 2 | 512 | 2 MiB |
| 4 | 1024 | 4 MiB |

**2 MiB 只是当前 `q=2` 的派生结果，不是设计常量。**

## 4. 8-core cooperative MM

每个 producer launch 只处理一个 communication batch，但该 batch 是一个
**8-core cooperative MM**，不是 8 个独立小 GEMM。

目标：

```text
A [BATCH_M, 2048]
B [2048, 2048]
        |
        | 8 AI Core cooperative MatMul
        | baseM/baseN/baseK = 256/256/64
        v
C [BATCH_M, 2048] -> send_arena[batch]
```

实现要求：

- `blockDim = 8`；
- `TCubeTiling.usedCoreNum = 8`；
- 8 个 block 使用同一个 logical A/B/C batch；
- 不再出现 `block1..7 + rt.usedCoreNum=1`；
- core0 与其它 7 核承担同等 MM 计算职责。

最终 core 到 C tile 的实际映射以当前 dav-2002 MatMul tiling 为准，不在协议层
假设固定 `1x8` 或 `2x4`。实现必须从同一 tiling 方案确定各 core 的输出 ownership。

## 5. MM 完成、cache 可见性与 signal

每个 batch 使用 8 个独立 64B ready cell：

```text
ready[core0..core7]
```

建议 ready 写入 batch generation，而不是每次 host 清零：

```text
generation = batch_seq + 1
```

每个 core：

```text
完成自己的 MM fragment
-> clean 自己产生的 C 数据
-> ready[core] = generation
```

core0：

```text
完成自己的 MM fragment
-> clean
-> ready[0]
-> 等待 ready[0..7] == generation
-> smem_shm_sdma_signal(batch_src, peer_batch_dst, batch_bytes, batch_id)
-> producer kernel 返回
```

### cache 纪律

最终性能实现应由**实际写该 C 区域的 core**清对应输出区。

若首版无法可靠获得 MatMul core→C tile ownership，可以在 bring-up 阶段让每个
参与 MM 的 core 在完成后 flush 自身 data cache，先保证 SDMA 可见性；该方式只作为
correctness fallback，最终必须用 profiler/tiling 明确 ownership 后优化 clean 范围。

## 6. 三级流水：MM -> SDMA -> Reduce

不需要引入复杂常驻 kernel。沿用当前单 execution stream，通过多个较粗粒度 kernel
launch 构建静态流水。

以 lookahead=1 为例：

```text
gate(wave)

P0: 8-core MM batch0 -> signal0
P1: 8-core MM batch1 -> signal1      || SDMA0
W0: wait/validate batch0
A0: reduce batch0                    || SDMA1

P2: 8-core MM batch2 -> signal2      || SDMA1(若仍在进行)
W1: wait/validate batch1
A1: reduce batch1                    || SDMA2

P3 ...
...
drain remaining wait/add

quiet(all outbound)
ack(wave credit)
```

目标形成两类稳定 overlap：

```text
MM(batch n+1)     || SDMA(batch n)
Reduce(batch n)   || SDMA(batch n+1)
```

第一版**不要求 MM 与 Reduce 同时占用 AI Core**。两者均可使用全部计算资源，
避免为了三路同时执行再次破坏 MM 效率。

如果实机证明单个 batch 的 SDMA 尚未被一批 MM 时间覆盖，可再比较
`lookahead=1/2`；默认先保持 1。

## 7. Wait / Reduce 重构

当前：

```text
producer(all chunks)
-> quiet
-> wait(all chunks)
-> add(whole wave)
```

改成：

```text
producer(batch)
-> wait_one(batch)
-> add_one(batch)
```

其中 `wait_one` 只消费一封 data mail，并严格校验：

```text
status == OK
dst == expected_recv_batch
len == batch_bytes
imm == batch_id
```

`quiet()` 不再放在每个 batch 前，而在 wave drain 后执行一次，用于证明本端所有
outbound 数据已落地、send arena 可安全进入下一 wave 复用。

现有 multi-block FP16 add kernel 可继续复用，只需增加 send/recv/output batch offset
和 valid rows 参数。

## 8. Arena 与 wave：与 batch 解耦

当前：

```text
arena_bytes = 64 * chunk_bytes
```

会导致增大 MM tile 时 arena 按比例膨胀。下一版必须解耦：

```text
row_bytes      = N * sizeof(FP16) = 4096
arena_rows     = 由 LOCAL_BYTES / 内存预算决定
arena_bytes    = arena_rows * row_bytes
wave_rows      = floor(arena_rows / BATCH_M) * BATCH_M
batches/wave   = wave_rows / BATCH_M
```

要求：

- `arena_rows` 必须是 `BATCH_M` 的整数倍；
- batch 大小变化不得自动放大 send/recv arena；
- 性能配置可继续保留当前 `tile_m=128` 实测时等价的 8192-row arena
  （send/recv 各 32 MiB，约 96 MiB local pool）；
- 小内存配置可用更小 arena，通过 multiple waves 工作。

`VLLM_ASCEND_MF310P_MAX_CHUNKS=64` 不再作为计算切块语义，新的 wave 容量以
arena 实际可容纳 batch 数为准。

## 9. Fixed credit 保持 wave 级

第一版继续：

```text
gate CREDIT
-> batch pipeline
-> all batch reduce done
-> quiet outbound
-> ack CREDIT
```

即使 batch0 已经提前 reduce 完，也不在同一 wave 内提前复用 peer recv slot。

原因：

- 当前 arena 容量足够；
- wave-level credit 已实机验证；
- 不增加 data/credit mail 混排复杂度；
- ACL Graph replay 语义保持简单。

只有后续要把 arena 缩成 ping-pong/ring 小槽时，才引入 per-slot credit。

## 10. Tail

正常 batch 始终按 `baseM` 对齐。

尾部：

```text
valid_rows
-> ceil(valid_rows / baseM) * baseM
-> zero pad
-> cooperative MM
-> signal aligned payload
-> reduce aligned payload
-> output 只写 valid_rows
```

为减少 Graph 分支，第一版推荐尾 batch 直接 pad 到完整 `BATCH_M`；不允许回退到
32/64/128-row 独立单核 MM。

## 11. Runtime / ABI 变更

建议 adapter ABI 从 v6 bump 到 v7。

参数语义从：

```text
tile_m
chunk_bytes
chunk_count
max_chunks
```

迁移为：

```text
base_m                  // 目标固定 256，不作为普通运行时调优项
batch_basem_count       // 1/2/4，默认首测 2
batch_m
batch_bytes
arena_rows
batch_count
valid_rows_last_batch
```

建议新增调优环境变量：

```text
VLLM_ASCEND_310P_MEMFABRIC_O_PROJ_BATCH_BASEM_COUNT=2
```

现有：

```text
VLLM_ASCEND_310P_MEMFABRIC_O_PROJ_TILE_M
```

在新 ABI 中应退出核心设计，只保留短期兼容/迁移逻辑或直接废弃。

以下保持：

- `VLLM_ASCEND_310P_MEMFABRIC_O_PROJ_MIN_M=4096`；
- warmup fallback；
- trace；
- feature gate；
- eager single-stream / ACL Graph capture-side-stream 合同。

## 13. 实施顺序

### P0：先恢复 MM

只实现：

```text
8-core cooperative MM
+ core0 signal
+ batch = q * baseM
```

暂时仍可 wave 末统一 wait/add。

Gate：新 producer 的纯 MM 时间必须接近 stock `F.linear/aclnnMm`，否则不进入
下一阶段。目标在 M=4096/6144/8192 上 MM median 相对 stock 不劣于约 5%。

### P1：batch wait + batch reduce

加入：

```text
P0 -> P1 -> W0/A0 -> P2 -> W1/A1 ...
```

用 profiler 证明两类 overlap。

### P2：调优

只调：

- `BATCH_BASEM_COUNT = 1/2/4`；
- pipeline lookahead = 1/2；
- arena_rows；
- per-core clean 范围。

不再通过减小 MM tile 制造 overlap。

## 14. 验收

### Correctness

至少新增边界：

```text
M = 255, 256, 257,
    511, 512, 513,
    1024, 2048, 4096, 6144, 8192
```

要求两 rank bit-exact、tail/multiple-wave/repeated call 全通过。

### Profiler

必须看到：

```text
SDMA(batch n) overlaps MM(batch n+1)
SDMA(batch n+1) overlaps Add(batch n)
```

并确认 8 个 AI Core 均参与 MM，没有专职空闲 communication core。

### Performance

重点比较三组：

```text
A: stock F.linear + HCCL
B: 当前 ABI v6 7+1 chunk pipeline
C: 新 ABI v7 8-core batch pipeline
```

至少记录 M=4096/6144/8192：

- MM duration；
- signal-to-arrival 暴露时间；
- batch add；
- fused total；
- stock total；
- Qwen eager TTFT / prefill tokens/s。

新设计必须先明显改善 B 的 MM 效率，再讨论通信收益。

### Stability / Graph

继续满足当前 Gate：

- >=1000 repeated；
- >60s / 10min；
- minimal + Qwen ACL Graph；
- strict mail validation / fail-stop；
- R6（约 20s engine freeze）未解除前不得判定可生产化。

## 15. 不做的事

本轮明确不做：

- 不保留专职 communication AI Core；
- 不做多个 AI Core 并发 `signal()`；
- 不再以 32/64/128-row 独立单核 GEMM 作为主 overlap 手段；
- 不把 2 MiB 写死为通信/规约协议；
- 不修改或读取 MemFabric private transport；
- 不在第一版引入 batch-level credit；
- 不为了三路同时执行强行并发 MM 与 Reduce。

## 16. 最终定义

下一版数据流统一为：

```text
8-core cooperative MM
        |
        | q * baseM rows ready
        v
core0 signal
        |
        +---------------- SDMA ----------------+
        |                                      |
next 8-core MM                          wait peer batch
                                               |
                                               v
                                      8-core batch reduce
```

核心原则只有一句：

> **以原生 MatMul tiling 为计算基线，以整数个 baseM 为通信/规约 token；8 核全部参与 MM，
> core0 只兼任 signal owner，SDMA 分别与下一批 MM 和上一批 Reduce 重叠。**
